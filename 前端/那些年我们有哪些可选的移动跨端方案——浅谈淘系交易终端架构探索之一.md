从 2007 年第一代 iPhone 正式发布开启移动互联网时代到现在已经有 17 年，为了解决移动端效率与体验问题，业界诞生了非常多的方案。每个方案都是站在巨人的肩膀上前行，这是最好的时代，这是变化最多的时代。

我的团队从 2019 年开始，曾经负责首页、信息流、店铺、详情等淘系电商基础产品业务，目前主要支撑交易业务。过往为了取得终端用户体验与研发效率的平衡也做了非常多的探索，也踩了不少坑；本文是淘系交易终端架构探索系列的第一篇，主要聊聊终端架构选型与技术演进。

![[aed21c51-7ecc-4cc4-a2aa-e31069b767d5.png]]

## 移动端的特点

移动设备存在低带宽，高延迟，小内存，低处理器性能等问题，在使用方式上具有随身携带，使用时间和使用场景更加碎片化的特点：

●

网络复杂：相比于 PC，由于手机设备持续处于移动过程，网络环境更复杂，网速不稳定、带宽低且延迟长；设备可能处于 wifi、2G、3G、4G、无网络、弱网络、wifi切换运营商网络、运营商网络切换wifi、运营商又包括联通，电信，移动等等

●

设备性能弱：PC x86 架构性能好，电耗高，存储空间大；移动设备使用 ARM架构耗电少、电压低，但是单核性能不如 X86。

●

传感器多：移动设备对比 PC 具有更多的传感器，包括摄像头、陀螺仪、加速度、GPS、磁力传感器等，例如，扫码支付、微信摇一摇等。

![[7d521028-9e1e-451c-942a-025e42a8bbee.jpeg]] ●

交互模式差异大——从鼠标到触屏：在PC设备上主要就是借助键盘和鼠标进行操作，包括单击、双击、右键、悬停、拖动等。移动端用户主要是以触屏和页面交互， [交互手势](https://developer.apple.com/cn/design/human-interface-guidelines/gestures#Standard-gestures) 有轻点、轻扫、双击、拖拽、缩放、捏住（按住）、旋转等等方式进行。另外，移动设备输入效率对比 PC 成本更高。

![[85d5539d-4d59-4775-8793-f3494e4d5a3b.png]]

## 移动开发面临挑战

●

跨端：一套代码多端部署与运行

●

动态性：支持远程加载资源进行热更新

●

研发效率：便捷的开发、调试与部署环境；发版周期短；

●

性能&体验：具备良好的加载性能与 Android/iOS Native UI 的交互体验；

●

开发者生态：是否跟已有的开发生态对接，对开发者是否友好；

●

稳定性：技术架构稳定，包括内存、CPU、Crash 等；

●

包大小：是否增加额外的客户端包大小以及磁盘占用；

### H5 Hybrid & Windvane——WebView 渲染

移动时代到来大家最先想到，也是最顺理成章的模式是将 PC 的研发模式移植到移动端。2009 年，Apache Cordova，旧称 PhoneGap是一款开放源代码的移动设备开发框架，旨在让开发者使用HTML、Javascript、CSS等Web APIs开发跨平台的移动设备应用程序。应用程序在针对每个平台的包装器中执行，并依靠符合标准的 Bridge API 绑定来访问每个设备的功能，例如传感器、数据、网络状态等。淘系也在 2013 年 ALLIN 无线开始建设自己的 Windvane 容器。

![[ac35856f-4590-49f6-a424-41f049facee3.svg]]

借助 Web 天然跨平台的特点，这套方案在跨端与动态性方面具有明显的优势；但在性能与体验方面遇到比较多的挑战，很长时间内，H5 给大家留下的印象就是性能差。尤其是 Facebook Zuckerberg 在 2012 年 『I think the biggest mistake we made as a company is betting too much on HTML5 as opposed to native』，给 H5 蒙上了长时间的阴影，在 [业界引发热议](https://www.infoq.cn/article/2012/10/facebook-html5) 。

●

页面打开慢，白屏时间长：在移动端盛行时，PC 的 Web 的渲染架构已经从传统的 SSR 转到 CSR。这套架构的优势是前后端分离，借助 V8 等 JS 引擎强悍的性能，在 PC 上 CSR 性能并不差。在移动端，由于设备性能、网络延迟与带宽对比 PC 有很大差距，而 H5 CSR 渲染模式需要加载过多的远程资源（HTML/JS/CSS/Mtop/图片）加剧了性能问题；即使是 2024 年的今天，Android 低端机或者弱网，H5 页面的打开性能依然惨目忍睹。

●

交互效果差，跟手响应慢：从 1990 年诞生第一个浏览器开始，浏览器已经在 PC 从幼年走向壮年；为了在手机设备上浏览网页，Android 与 iOS 使用 WebView 在 APP 内嵌入网页。将 Web 方案移植到移动端环境之后，由于交互模式的巨大变化引发了一系列水土不服的问题。例如，长列表滚动白屏、点击 300ms 响应延迟、点击穿透、1px 边框、输入框飘了、键盘被遮挡等。

○

长列表滚动白屏：早期 iOS WebView 下滚动事件 scroll 在滚动过程中不会触发，只有在滚动停止时才触发。久其原因是设备性能较差，在页面滚动时，JS 停止执行，直观表现是滚动长时间白屏；同时，没有 Native 的 cell 的复用回收机制，无线滚动渲染也带来了内存问题。

○

点击响应延迟：这要追溯至 2007 年初。苹果公司在发布首款 iPhone 前夕，遇到一个问题 —— 当时的网站都是为大屏幕设备所设计的。于是苹果的工程师们做了一些约定，应对 iPhone 这种小屏幕浏览桌面端站点的问题。这当中最出名的，当属双击缩放(double tap to zoom)，由于用户可以进行双击缩放或者双击滚动的操作，当用户一次点击屏幕之后，浏览器并不能立刻判断用户是确实要打开这个链接，还是想要进行双击操作。因此，iOS Safari 就等待 300 毫秒，以判断用户是否再次点击了屏幕。

○

交互不跟手：由于浏览器 UI 主线程与 JS 线程互斥，在用户进行跟手、拖拽、多指等操作过程中，无法在一帧内完成 JS 执行+UI布局，常常导致动画卡顿与掉帧。

●

多媒体兼容性差，视频无法播放是常态：由于 Android 厂商对 [video 的适配不佳](https://ata.atatech.org/articles/11000040615?spm=ata.25287382.0.0.3a0a1838Cbvl6W) ，支持的视频文件格式、播放控件实现不一致，经常出现视频在这个设备可以播放在另外一个设备黑屏的问题；同时，由于 iOS 系统限制，默认自动播放能力也是不支持。

●

定制能力弱，功能障碍很难克服：由于浏览器过于复杂，当遇到功能或者体验问题时，几乎无法通过修改源码来实现定制。

●

内存等问题引发的稳定性隐患：由于移动设备内存有限，WebView 内存问题常常引发 OOM 与 Crash 问题。

为了解决上述问题，业界也是前仆后继做了非常多的探索：

●

白屏&首屏：

○

离线包：为了解决首屏问题，将 HTML/JS/CSS 打成一个资源包提前内置到 APP 中，当用户访问时直接从本地读取资源从而加快首屏打开速度。例如，手淘的 zcache 方案。详细可以参考， [高扩展 & 高性能的 Hybrid 混合式开发](https://ata.atatech.org/articles/11000016984?spm=ata.25287382.0.0.7ad825e7rVSVAE) 。这个方案挑战是包大小与命中率之间的权衡，对大流量业务收益很明显，但小流量业务往往命中率过低。

○

SSR：随着 NodeJS 与前后端框架同构渲染方案的逐步成熟，淘系也在尝试使用 Node SSR 来解决性能问题。对比 CSR，SSR 可以在 HTML 请求返回后立马渲染上屏且不受访问量大小的影响，但真实可交互依然需要在 Hydrate 之后。详细参考—— [2020双十一会场性能优化-SSR的思考与总结](https://ata.atatech.org/articles/11000186033?layout=%2Fvelocity%2Flayout%2Fblank.vm)

●

混合渲染：为了解决多媒体播放问题，经典做法是用 Native 开发播放器组件，然后使用混合渲染的模式，将Native组件嵌入到 WebView 中。具体方案又分为盖在 H5 页面上，但滚动不跟随；或者参与 WebView 的布局，但会存在多种不同来源渲染内容合并引发的性能问题，进而导致滚动不流畅。参考， [【U4混合渲染系列1】混合渲染嵌入式View介绍](https://ata.atatech.org/articles/11000124944?layout=%2Fvelocity%2Flayout%2Fblank.vm) 。备注：UC 内核使用自研的 Apollo 播放器，用于 夸克 / UC 等各类场景中，在音视频兼容性上比较好。但在手淘中，由于包 Size 等约束要求，目前是没有使用 Apollo 播放器（而是降级使用了系统自带的 MediaPlayer）。UC 内核在音视频托管方案实现上，跟其他场景的混合渲染不太一样，UC 内核可以支持多种不同模式的视频托管，包括仅托管视频解码器，但渲染仍由 Web 内核连通其他 Dom 元素一起渲染的方案，这个方案在性能上是能做到优于采用 Native VideoView 的混合渲染方式的。

●

交互体验：为了解决交互与响应慢的问题，也是探索了一系列方案， [手机端H5页面呼出键盘问题](https://ata.atatech.org/articles/11000038690?spm=ata.23639746.0.0.7bc9e66az41u1r) ， [无线端滚动实践](https://ata.atatech.org/articles/11000021306?spm=ata.23639746.0.0.7868670fdkrJJL) ， [300 毫秒点击延迟的来龙去脉](https://ata.atatech.org/articles/11000014933?spm=ata.23639746.0.0.7868670fdkrJJL) ， [无线H5难题解决-如何优化h5页面渲染前的白屏](https://ata.atatech.org/articles/12000020999?spm=ata.23639746.0.0.2ed83ef2MR6qri) ， [淘宝双11无线页面性能优化总结](https://ata.atatech.org/articles/11000044599?spm=ata.23639746.0.0.23b224fa1SsV7Q#MTVlMjBl) 等。

●

稳定性：iOS 使用 [WKWebView](https://ata.atatech.org/articles/11000024193) 替代 UIWebView ， [Android 的 UC 的多进程方案](https://ata.atatech.org/articles/11000153439?layout=%2Fvelocity%2Flayout%2Fblank.vm) 等方案。

过去的十年，H5 页面的很多体验问题已经在浏览器层面被彻底解决，例如，300ms 延迟、滚动白屏。不少问题还在解决的路上，例如，白屏问题、视频播放器问题；但有些问题当前依然看不到有效的解决方案，例如，由于缺少精细化的手势控制能力，无法做到流畅的跟手交互。

### React Native & Weex 1.0 & DX——Native UI 渲染

#### RN & Weex 1.0

由于 Web 存在短时间内无法克服的问题，即原生控件的交互体验、手势识别以及线程模型。我们能否实现 Web 的开发体验，同时兼具 Native 的体验。 React Native 就在这个背景条件下诞生了 。 [React Native](https://engineering.fb.com/2015/03/26/android/react-native-bringing-modern-web-techniques-to-mobile/?spm=ata.21736010.0.0.52b814a3BV97Y1) (简称RN) 是Facebook于 2015 年 4 月开源的跨平台移动应用开发框架，使用 JavaScript 语言，类似于 HTML 的 JSX，以及 CSS 来开发移动应用，支持 iOS 和安卓两大平台。

![[09135c7d-63e8-49f5-b08c-d047dbc48c08.png]]

淘宝也在 2015 年发布了 Weex 1.0，并在 2016 年双十一大促会场中大规模使用。其优点如下：

●

跨端：Learn once, write anywhere，支持跨 Android/iOS 两端；Weex 支持跨三端（H5）。

●

原生体验：由于 RN 组件就是对原生视图的封装，因此使用 RN 编写的应用视觉、交互和性能与原生应用一样。例如，长列表滚动。

![[d94c60da-05c7-41ba-9f19-c35442d23da6.svg]] ●

兼容与定制：如果已有能力无法满足，可以很便捷的新增与封装新的 Native Module 与 Native UI；同时，RN 的项目可以无缝兼容现有的 Native 项目

●

开发者体验：通过 Yoga 支持 Flexbox 的布局模式以及热重载的机制，让熟悉Web前端开发的人员只需少量的学习就可以进入移动应用开发领域

随着在业务中大规模使用 RN（Weex 1.0），也逐步暴露了这套架构下的问题：

●

多端一致性：由于 Android 与 iOS 平台特性并不完全一致，导致很多能力无法做到双端完全一致；例如，富文本，常见的图片与文字同行渲染，只能使用计算字符长度来近视处理边距；

●

富交互&动画：由于需要频繁的使用 JS Bridge 进行 JS 与 Native 层间的通信，动画很难做到到 60FPS；

●

性能问题：使用 JSX 书写的声明式 UI 很容易导致层次嵌套过深，从而引发性能问题；在低端机上，由于架构机制问题，性能对比 Native 有差距；

●

开发&调试：JS 断点调试能力弱，很多情况下只能打 console.log

●

包大小：无论是早期的 V8 还是 JavaScriptCore 等都存在较大的包体积

为了解决上述问题，淘系也探索 [基于bindingx 的 Weex的创新交互体验](https://ata.atatech.org/articles/11000073261?layout=%2Fvelocity%2Flayout%2Fblank.vm) ，原生框架的 [Weex Eagle](https://ata.atatech.org/articles/11000136157?spm=ata.23639746.0.0.5e7f3233NmjDtZ) ， [轻量级 JS 引擎 QKING](https://ata.atatech.org/articles/11000184682?spm=ata.25287382.0.0.54fc5ed6RnG8yJ) ；对应到 RN 也有基于 C++ 的 Fabric 架构以及 Hermes JS 引擎等。

#### DinamicX

[DinamicX](https://ata.atatech.org/articles/11000231101) 提供多端一致的客户端动态模板解决方案，支持 Android/iOS/鸿蒙/H5。DinamicX 最初诞生于手淘首页，为了提供高性能，DX只支持UI的动态化，有限的逻辑控制只能通过表达式来实现；DinamicX 具备以下优点：

●

跨端：一个 DinamicX 模板，支持 Android/iOS/h5/小程序；

●

动态化：支持动态下发模板，来实现 UI 与部分逻辑的动态化；

●

高性能：在端侧使用 Java（Android）、Object-C（iOS）等原生语言驱动 Native UI 的渲染，对比 RN 等方案减少了语言间的通信开销；

![[8d971e3c-dade-4399-bd14-d0938d5d8586.webp]]

由于使用类 Android XML 的私有 DSL，对开发者并不友好；同时，为了高性能只能支持有限的动态性，依然需要进行多端开发，为了增强动态性，也探索了 [事件链](https://ata.atatech.org/articles/11000230813?spm=ata.21736010.0.0.1b76c711RJaLSa&layout=%2Fvelocity%2Flayout%2Fblank.vm) 、DinamicX + QKing 的方案；

### 小程序 & PHA——应用级解决方案

#### 小程序

微信小程序是腾讯于2017年1月9日推出的一种不需要下载安装即可在微信平台上使用的应用程序，主要提供给企业、政府、媒体、其他组织或个人的开发者在微信平台上提供服务。

关于小程序的准确定义可以参考 [张小龙 2017 微信公开课](https://www.sohu.com/a/287860269_358836) 『小程序是一种不需要下载、安装即可使用的应用，它实现了触手可及的梦想，用户扫一扫或者搜一下就能打开应用，也实现了用完即走的理念，用户不用安装太多应用，应用随处可用，但又无须安装卸载』。至于为什么要做小程序，张小龙的回答是『本质上来说，我们更希望在智能手机里用户可以更快捷的获取服务，但是他的体验又比网站要好很多很多，同时他的麻烦程度又比他去下载一个APP要好很多很多，它不像下载一个APP那么麻烦，这个就是小程序的定位』。 在技术上，微信期望使用小程序解决之前 JS-SDK 无法解决的问题，包括：

●

快速的加载

●

更强大的能力

●

原生的体验

●

易用且安全的微信数据开放

●

高效和简单的开发

小程序的运行环境分成渲染层和逻辑层，由2个线程管理，其中 WXML 模板和 WXSS 样式工作在渲染层，JS 脚本工作在逻辑层。渲染层的界面使用了WebView 进行渲染；逻辑层采用JSCore 线程运行 JS 脚本。一个小程序存在多个界面，所以渲染层存在多个WebView线程，这两个线程的通信会经由微信客户端做中转，逻辑层发送网络请求也经由Native转发，小程序的通信模型下图所示， [参考](https://developers.weixin.qq.com/miniprogram/dev/framework/quickstart/framework.html#%E6%B8%B2%E6%9F%93%E5%B1%82%E5%92%8C%E9%80%BB%E8%BE%91%E5%B1%82) 。

![[3ef0255b-8589-4e26-9e54-db93723aa9f2.png]]

从技术的角度看，小程序具备以下优点：

●

研发效率：几乎具备 H5 Hybrid 的所有优点，包括端能力增强、跨端、接近 Web 的研发体验；

●

应用级体验：在小程序之前，H5 Hybrid 还是 RN 的方案偏向提供的是页面级别的解决方案；小程序的设计是应用级别一体化的方案，包括默认离线包、标准化的转场动画等

●

开放&隔离：为了保障安全，JS 跑在 Worker 线程里，即无法直接访问 DOM，即实现了物理隔离。

●

扩展性：渲染层的抽象，让后续使用 Native 组件替换部分 UI 组件，甚至替换渲染引擎存在更多的可能，例如 [Skyline](https://developers.weixin.qq.com/miniprogram/dev/framework/runtime/skyline/introduction.html) 。

小程序技术的诞生完全是为了解决微信三方开放问题的，为了保障安全，不可避免的需要更多的管控与限制；从加载性能的角度看，由于是访问时安装，且需要拉取拉群小程序相关的配置，从性能上对比普通的有 zcache 的 H5 并没有优势；由于默认使用 WebView 渲染，H5 Hybrid 有的问题几乎都有，甚至采用双线程模式，问题会更加突出。

#### PHA

如果说小程序是面向三方的应用级解决方案，那么 PHA 可以类比为面向二方应用开发的解决方案。 [PHA](https://ata.atatech.org/articles/11000253910?spm=ata.23639746.0.0.4f0735658dMM2f) 全称是 Progressive Hybrid App，是提升 Hybrid 体验的一种开箱即用的 Web 容器框架。在遵循 Web 标准的同时，提供了渐进式增强的策略和性能极佳的富交互组件来创建 Hybrid 应用，使得这些应用能够无缝使用 Web 的技术栈的同时具有接近 Native 的用户体验。

![[4242dab6-edb2-4fc4-ac7f-fcca6e9fa57b.png]]

PHA 除了具备 H5 Hybrid 应用的优点之外，还具备以下优势：

●

应用级交互体验：支持多 Tab、Swiper、沉浸式状态栏、下拉刷新、启动屏等

●

性能增强：支持业务配置多种性能优化方案，包括数据预请求、HTML 模版化、离线资源、Manifest缓存等

●

调试增强：使用 AppDevTools 可以很方便的调试与排查问题

详细可以参考： [速度与激情：PHA 用户体验提升之道](https://ata.atatech.org/articles/11000211675?spm=ata.23639746.0.0.4f0735658dMM2f) ， [PHA 2.0 全面升级，将体验优化进行到底](https://ata.atatech.org/articles/11000223699?spm=ata.23639746.0.0.4f0735658dMM2f) 。在劣势方面，由于使用 WebView 渲染，单页面内的交互 H5 Hybrid 的问题几乎都有；同时在单页面的加载性能上对比 Windavne 几乎没有收益，甚至由于 manifest 的引入性能可能会更差；

### Flutter & Weex 2.0——自绘渲染

#### Flutter

Flutter 是一个跨平台的 UI 框架，使用一套代码开发 Android、iOS、PC 应用，通过直接与底层平台服务（GPU/CPU）进行交互，从而实现高性能。Flutter 的创始人 Eric Seidel 是 Google Chrome 团队的成员，在渲染领域有十几年的工作经验，Flutter 他觉得是 where my leverage is。Flutter 项目的诞生源于他与团队为了让 Web 体验更顺滑，他进行了一项大胆的实验。他移除了浏览器中大量的兼容性代码和一些不常用的功能，并进行了基准测试。结果令人振奋，许多他们关注的性能指标提升了整整 20 倍。由此，他和团队投入了大量时间深入研究，最终孕育出了 Flutter。

不同于 RN，Flutter 选择 Dart 而不是 JavaScript 作为首选编程语言。早期项目也在使用 JavaScript，但由于性能问题，在使用 JavaScript 实现之后，启动时间接近 12 秒；这与 Flutter 期望达到甚至是超越 Android/iOS 原生的性能体验有 gap；于是在项目推进过程中选择了 Dart，因为其能针对 Flutter 的场景做优化，且支持 AOT 和 JIT 模式；在开发阶段用 JIT 提升效率，在部署阶段使用 AOT 提升性能。详细材料可以参考 [1](https://www.youtube.com/watch?v=h7HOt3Jb1Ts&t=2s) ， [2](https://semaphoreci.com/blog/multi-platform-development-co-creator-flutter-eric-seidel) ， [3](https://flutter.dev/) 。

![[ec18b229-cdf7-4deb-af92-fff6a9cf2a20.png]] ●

跨端：支持 Android/iOS/Web/Windows/macOS/Linux Desktop 等多个平台；

●

多端一致：使用自绘UI引擎原生方式做渲染，底层对接 Skia 与 Impeller；

●

高性能：Flutter 应用程序会直接编译为机器代码（Intel x64 或 ARM 指令集），同时，没有 JSBridge 这一层的通信开销；

●

开发效率：支持热重载，大大提高了开发效率；

Flutter 虽然很美好，但也有自己的一些问题：

●

交互体验：无法享受已有技术体系的优化成果，所有的组件都需要从 0-1 重新建设；同时，由于渲染模式跟 Native UI 不一致，无法享受操作系统层面的优化，部分资源需要启动时才能加载与准备好；

●

研发体验：没有使用 Web 体系，Dart 无论对前端还是客户端都需要重新学习一门新的语言；

●

已有体系融合困难：虽然提供了一系列的混合渲染方案，但没有一套方案可以完美解决所有问题；

●

稳定性&包大小：相对于 Native 或者 RN，由于 iOS 渲染存在上屏三缓存的机制，内存占用会更大；集成 Flutter 会显著增加包大小

●

动态性：默认不支持动态下发，虽然业界有各种各样绕过去的方案。

#### Weex 2.0

Weex 2.0 是 Weex 自诞生以来最大的架构改造，自研脚本引擎和渲染引擎，更贴合 W3C 标准，引入字节码、自绘渲染、原生框架、Canvas 等方案，在兼容 1.0 的基础上，彻底解决跨端一致性差、样式能力不足问题，核心策略， [参考](https://ata.atatech.org/articles/11000232464?layout=%2Fvelocity%2Flayout%2Fblank.vm) ：

●

标准：对接 Web 标准子集（W3C/TC39），与前端生态（高研效工程技术）打通。

●

自研：内核自研，技术上可持续深入，结合场景诉求灵活扩展和定制，减少不可控因素。

●

C++：全面 C++ 化，可跨多端多系统，新系统可低成本移植。

![[46c9b633-3149-49f5-ac4f-d52af1ad00f1.jpeg]]

某种意义上，Weex 2.0 在 Flutter Engine 的基础上实现了一个微型浏览器引擎。在具备 Flutter 的优点的同时加强了以下能力：

●

研发体验：对接 Web 标准子集（W3C/TC39），让前端可以无缝使用 Weex 2.0 开发；同时， [支持 Chrome Debug Protocal](https://ata.atatech.org/articles/11000225635?layout=%2Fvelocity%2Flayout%2Fblank.vm) ，能够使用Chrome提供的全套断点调试能力；

●

动态性：跟 H5 或者 RN 一样，支持通过动态下发 JSBundle；

●

性能：在 quickjs 上自研了 QKing JS 引擎，支持下发 [字节码](https://ata.atatech.org/articles/11000243425?spm=ata.23639746.0.0.1fbe412alWi5GT) ，可以减少 JS 执行时的解析时间。

但没有了 Dart 的 AOT 能力，且没有 V8 或者 JavaScript JIT 能力，QKing 在执行性能上是没有优势的；同时，由于采用自绘的模式，Flutter 面临的交互体验、已有体系融合、内存与包大小相关的问题依然存在。

## 总结

过去十年，从渲染机制上可以分为：WebView 渲染、Native UI 渲染与自绘渲染；从解决方案上可以分为组件级、页面级与应用级。具体使用哪套方案即取决于业务场景，也取决于团队的人才结构；没有最好的方案，只有最合适的方案。我们的选择是什么，请移步： [那些年我们都做了哪些尝试——浅谈淘系交易终端架构探索之二](https://ata.atatech.org/articles/11020332007?spm=ata.25287382.0.0.2f4f1838ZDIuV5) 。

●

React Native（Weex 1.0） & DinamicX（以下简称 DX）：二者从底层原理上没有本质的区别，都是采取自定义 DSL 对接 Native UI；DX 在 Framework 层面使用的是原生语言实现，少了 JSBridge 带来的通信开销，所以 DX 的性能上限会更高。但过多的 DX 模板个数以及越来越复杂的 DX 模板也在抵消这个优势。如果 DX 最开始使用类似 JSX 的 DSL，也许对 DX 和 Weex 1.0 会有不一样的结果。

●

Fultter & Weex 2.0：渲染管线是比较精简的，这是高性能的前提；二者使用相同的底层 Flutter Engine，只是对接开发者生态部分二者有明显的差异；

●

Weex 2.0 & H5：二者都是对接 W3C 生态，都走自绘的模式；Weex 2.0 对比 H5 的优势在于没有历史包袱，自研可定制（类似 BindingX），小步快跑（浏览器背后的标准化组织的参与方之间博弈）；劣势在于浏览器与 Native UI 踩过的坑都要再踩一遍；

●

H5 & 小程序：从渲染模式上，由于 MiniApp Framework 双线程的机制，小程序从绝对性能上一定是没有 H5 好的。但小程序普遍给大家体验更好的印象是应用级解决方案带来的优势，包括默认的离线包机制、统一的转场动画与交互体验。

●

H5：浏览器诞生于 PC 时代，诞生的基因是鼠标、键盘、大屏与高性能；在移动端遇到的所有问题根源都在于此，当然浏览器也在逐步变好，期待更好的那一天。

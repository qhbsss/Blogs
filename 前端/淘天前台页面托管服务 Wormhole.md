## 概述

## 能力介绍

Wormhole提供了统一托管的页面渲染服务，用户能够轻松地应对高流量和对性能要求较高的页面场景，而无需关心繁琐的运维工作。最新支持的自适应渲染技术，可以根据不同的场景提供服务器端渲染（SSR）和客户端渲染（CSR）的切换，以实现高性能和低成本的需求。

在天马搭建的页面发布过程中，默认将页面发布到Wormhole上，实现了页面信息和数据源的动态注入。

## 问题分析

## 核心逻辑:

渲染服务本质是生成端侧需要的内容，如果是纯静态的内容，可能只需要一个 nginx 静态服务器就行了。 如果是搭建系统这样的需要动态的快速生成不同配置、不同数据的页面，并且保证页面的高可用、高性能，则需要一个独立的、功能强大渲染服务。

## 技术要点:

搭建的本质是配置 我们这里把搭建的产出物想象成你写的一个 JSON，里面声明了你想让这个页面的标题是 `你好，世界`

```{
{
  "title": "你好，世界"
}
```

这样的一个 JSON 如果无人解析它，它就只是一份数据。如果有对应的解析器，那如何书写这份 JSON 的规则就变成了一种简易的 DSL。

当 Web 服务器需要根据这份 JSON 生成一份带有 `<title>你好，世界</title>` 的 HTML 的时候，自然而然的就会有不同的实现路径

![](02608167-24af-47c4-874f-1776270f6119.jpg)

上图的两条路径是划分比较清晰的，主要的区别在于 Web 服务器是否会`承载生成逻辑`，相应的优缺点

|  | 优点 | 缺点 |
| --- | --- | --- |
| 在线解析 | 灵活，变更生效快，依赖环节少  例子：若想统一修改一批页面的 title，只需更改 HTML 生成逻辑即可  例子：突发修改需求，改后发布立即生效 | Web 服务器承受了计算压力 |
| 离线生成 | Web 服务器不承受计算压力，构建过程可以优化页面大小（tree shaking 等，在后续文章中将会展开讲） | 死板  例子：若想统一修改一批页面的 title，需要把这批页面全部重新发布一次 |

可以看到两种方式的优缺点都比较明显，在天马搭建的实际实现中两种方式均有体现或互相结合，但是总体上以 `在线解析` 为主，对应的 Web 服务器实现是 [Wormhole](https://pegasus.alibaba-inc.com/wormhole) 。

我们在具体的技术方案上的选择如下表

|  | 技术方案 | 原因 |
| --- | --- | --- |
| 端侧所需产物生成 | 基于动态模板的渲染生成方式：JavaScript 模板（如 xtemplate 这类可被编译成 js func 的模板，React 这类 SSR bundle 同理） | 灵活，更贴近端侧开发者 |
| JSON DSL | 天马 DSL | 没得选 |

基于这样的选择，我们可以向开发者提供能力，实现灵活的向端侧输出 HTML/JS/Other 类型的内容供端侧容器使用

![](b9d4c5d8-febb-47af-9b80-dc6af358a7c3.jpg)

## 详细方案:

#### wormhole 2.0 免运维的源站架构

![](fd16cad3-f78a-499a-b707-6a2632ed3119.jpg)

我们在中间增加了 CDN 这一层，具体 CDN 的原理及实现可以参考 [阿里云 CDN 文档](https://help.aliyun.com/product/27099.html)

|  | 优点 | 缺点 |
| --- | --- | --- |
| CDN | 1. 极大的降低源站压力，减少维护成本 2. 提供容灾能力，提升整体稳定性 3. 离端侧地理位置更近，延时更低 | 1. 在缓存周期内，页面等效于被静态化 2. 受缓存 key 限制，回源时源站能获取到的信息变少 |

优点是显而易见的，展开说一下第二个缺点。

CDN 缓存 key 的组成原理：一个 HTTP 请求到达 CDN 后，CDN 所能解析出的信息包括 `Path`，`Query`，`Header`。CDN 会依据一定规则使用它们拼接出缓存的 Key，如天马默认应用的规则为 (`Path`) + (`Header` 中的 `User-Agent` 字段所解析出的 设备类型) 构成缓存 key。

因此在回源时，模板代码所能获取到的 HTTP 请求的信息被限制为了上述构成缓存 key 的两样信息。这样会影响一定的灵活性，例如想实时根据 cookie 中的 userId 来返回不同内容的场景。

#### wormhole 3.0 去中心化的服务架构, 提供业务灵活的定制能力

基于 [Wormhole SDK](https://yuque.antfin.com/wormhole/next-generation/iav58f) ，我们可以让业务 构建一个属于自己的 Wormhole

![](a1861961-06be-4cdd-8a05-d2be8ff34caf.jpg)

我们抽出了模板渲染的能力，业务可以基于SDK定制逻辑然后部署在自己的服务器上，这样可以不受我们源站架构的限制，达到最大的灵活性

#### wormhole 4.0 自适应渲染架构

4.0 版本整合端上、ER、源站的能力，从体验出发， 结合流式SSR 的性能优势与Wormhole 的零运维能力，综合考虑服务成本，思考实现好的用户体验的最佳路径。

![](0c92a1ba-301d-4e28-89b4-4d7478b9aee4.jpg)

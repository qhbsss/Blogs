最近在看 Codex 里 `/goal` 的实现，越看越觉得这个功能被低估了。

很多人一聊 Agent 长任务，就会说：让它自己规划、自己执行、自己检查、一直做到完成。听起来很合理，但真正用起来，经常会出现几种很熟悉的情况：

它做着做着忘了最开始要干什么。

它明明只完成了一半，却开始写总结。

它遇到一个小问题，绕了十几轮还在证明自己“马上就好”。

你打断它之后，下一次恢复，它也不知道是该接着干，还是该先问你。

所以我一开始以为 `/goal` 只是一个“长任务提醒”功能：给线程挂一个目标，让 Agent 别忘了。

读完源码之后发现，不是。

先说结论：

Codex 的 `/goal` 不是 Todo，不是 prompt，也不是一句“继续做到完成”。它是一张 `thread_goals` 表，加一套状态机，加一套预算账本，加一套自动续跑机制。

换句话说，它不是在鼓励 Agent 更有毅力，而是在给长任务装刹车、仪表盘和交接单。

这篇文章就拆这个东西。

![[20ce2781-1d0a-4383-8169-7e829dc8e6c7.png]]

## 一、为什么很多长任务 Agent 不好用

在讲 `/goal` 之前，先说几个我觉得很常见的误区。

很多长任务 Agent 不好用，不一定是模型不够聪明，而是任务本身没有被工程化。

### 1\. 把目标写进 prompt，就以为 Agent 会记住

最常见的写法是：

请继续工作，直到任务完成。

或者更狠一点：

在满足所有要求之前，请勿停止。

这类话短期有效，长任务里很脆。

因为目标如果只存在于上下文里，它会被新消息稀释，被工具输出冲散，被压缩摘要改写，被模型自己的中间判断覆盖。对话越长，“最开始到底要做什么”就越像白板角落里那行字，会议开到第三小时，谁都知道它重要，但谁也说不清现在还剩哪些没做。

长任务的第一步，不是让模型更努力。

是让目标从聊天记录里出来，变成一个持久对象。

### 2\. 把“自动继续”当成自驱

很多系统所谓的长任务，其实只是模型一停，就再塞一句：

继续

这不是自驱，这是复读。

真正的问题不是“要不要继续”，而是：

●

现在有没有用户的新输入？

●

当前 turn 是否真的结束了？

●

目标有没有被替换？

●

预算是不是已经用完？

●

模型是不是在等用户选择？

●

当前模式是否允许它自己往前跑？

如果这些条件不检查，自动继续就会变成抢方向盘。用户刚想插话，它又开了一轮；用户已经打断，它还在做旧目标；模型其实需要用户确认，它却继续猜。

### 3\. 没有预算，就没有长任务

长任务一定会遇到成本问题。

不是抽象的“成本”，是真实的 token、时间、工具调用、上下文污染。

如果系统只在最后告诉你“这次用了很多 token”，那就太晚了。预算控制真正有价值的地方，是在任务中途知道已经花了多少，什么时候该收尾，什么时候该停下来等用户决定。

这就是 `/goal` 的切入点。

它不是给 Agent 加一句更强的口号，而是把长任务里最容易失控的几个东西拿出来，分别做成状态、账本和事件。

## 二、核心机制：一张表撑起长任务的骨架

我读源码时，最先让我觉得“哦，这不是玩具功能”的，是这张表：

CREATE TABLE thread\_goals (

thread\_id TEXT PRIMARY KEY NOT NULL REFERENCES threads(id) ON DELETE CASCADE,

goal\_id TEXT NOT NULL,

objective TEXT NOT NULL,

status TEXT NOT NULL CHECK(status IN ('active', 'paused', 'budget\_limited', 'complete')),

token\_budget INTEGER,

tokens\_used INTEGER NOT NULL DEFAULT 0,

time\_used\_seconds INTEGER NOT NULL DEFAULT 0,

created\_at\_ms INTEGER NOT NULL,

updated\_at\_ms INTEGER NOT NULL

);

看起来很普通，对吧？

但长任务系统最需要的，往往就是这种普通东西。

`objective` 记录目标， `status` 记录状态， `token_budget` 记录预算， `tokens_used` 和 `time_used_seconds` 记录消耗。每个线程只挂一个当前 goal，线程删除时 goal 也一起删除。

这里有两个细节很关键。

第一个是 `goal_id` 。

每次创建或替换目标，都会生成新的 `goal_id` 。后面做更新或记账时，可以带上 `expected_goal_id` 。如果中途目标已经换了，旧 turn 的账不会糊到新 goal 上。

这听起来像数据库工程细节，但长任务最怕的就是这种异步错位。

比如 Agent 正在执行一个旧目标，用户突然替换了目标。旧 turn 后面才返回工具结果。如果没有 `goal_id` 做保护，它可能把旧目标的 token、状态更新写到新目标上。你看 UI 会觉得系统疯了：我明明换任务了，为什么新任务已经花了 30K token？

第二个是 `status` 只有四种：

●

`active`

●

`paused`

●

`budget_limited`

●

`complete`

这四个状态很克制，但刚好够用。

`active` 表示可以继续推进。

`paused` 表示用户或中断让它先停。

`budget_limited` 表示目标还没完成，但预算到了。

`complete` 表示目标已经完成。

注意 `budget_limited` 和 `complete` 是分开的。

这点非常重要。很多系统会把“我不继续了”和“我完成了”混在一起，最后就会出现一种很尴尬的情况：Agent 预算用完了，然后写一段漂亮总结，好像事情已经完成。

Codex 这里的语义很清楚：

预算到了，不等于任务完成。

这一个状态就能避免很多自欺欺人的总结。

![[2f30df25-2208-4d25-ad3a-3f7c06818b25.png]]

## 三、骨架之外：三个工具决定模型能碰什么

有了状态还不够，关键是模型能不能乱改状态。

Codex 给模型暴露了三个 goal 工具：

1.

`get_goal`

2.

`create_goal`

3.

`update_goal`

这里最有意思的是 `update_goal` 。

它的 schema 里， `status` 只能是一个值：

{

"status": "complete"

}

也就是说，模型只能把目标标记为完成。

它不能暂停 goal。

不能恢复 goal。

不能把 goal 标成 `budget_limited` 。

不能随手改 objective。

`create_goal` 也有限制：只有用户或系统明确要求时才创建 goal，不要从普通任务里自己脑补一个 goal。并且如果当前线程已经有 goal，创建会失败，不会悄悄覆盖。

这个设计很像真实团队协作。

一个工程师可以说“这个需求做完了”，但他不能自己批准预算超支，也不能在你没同意的情况下把项目目标换掉，更不能遇到困难就把任务状态改成“暂停”然后消失。

在 `/goal` 里，权限是拆开的：

模型负责理解目标和判断完成。

用户负责暂停、恢复、清除、替换目标。

系统负责记账，预算到了就把状态改成 `budget_limited` 。

这个拆法很朴素，但比“相信模型自己守规矩”可靠得多。

我觉得这就是 Harness 里一个很重要的审美：不要把所有按钮都交给模型。

模型当然要有能力，但能力不等于权限。尤其是长任务，一旦模型既负责干活，又负责裁判，又负责预算，那它很容易在压力大的时候给自己判赢。

## 四、自我推进的闭环：不是“继续”，而是“有条件地继续”

`/goal` 真正有意思的地方，是它会在空闲时继续推进 active goal。

但它不是每次看到 active 就直接开跑。

源码里会先过一串条件：

●

goal 功能必须开启。

●

当前不能是 Plan mode。

●

当前不能已经有 active turn。

●

不能有排队的用户输入。

●

不能有 trigger-turn mailbox 里的待处理项。

●

线程必须是持久线程，ephemeral thread 不支持 goal。

●

数据库里读到的 goal 必须还是同一个 `goal_id` 。

●

状态必须仍然是 `active` 。

这才是真正的自动续跑。

不是“模型停了就催一句继续”，而是 Harness 判断现场确实空了、目标确实还在、用户确实没有新话要说、当前模式确实允许它自己推进，然后才启动一个 continuation turn。

这个 continuation turn 里，系统会注入一段 developer prompt。

这段 prompt 我觉得写得很值得抄。

首先，它把用户目标包在 `<untrusted_objective>` 里：

<untrusted\_objective>

{{ objective }}

</untrusted\_objective>

这说明 objective 是用户数据，不是更高优先级的系统指令。目标可以告诉模型要做什么，但不能趁机变成 prompt injection。

其次，它不是简单说“继续工作”，而是要求做完审计。

它会要求模型：

●

把目标重述成具体交付物或成功标准。

●

建一个 prompt-to-artifact checklist。

●

检查相关文件、命令输出、测试结果、PR 状态或其他真实证据。

●

不要把“做了很多”“测试过了”“看起来差不多”当成完成证据。

●

有任何缺口，就继续做，而不是标记完成。

这段很关键。

很多 Agent 长任务的问题，不是不肯继续，而是太容易宣布胜利。

它改了几个文件，跑了一个测试，看见绿色输出，就开始写“任务已完成”。但用户真正要的可能还有文档、边界 case、截图、发布说明、回归验证。

Codex 的做法是把“完成”变成审计问题：不是问 Agent 你觉得做完了吗，而是让它拿目标逐项对照现实证据。

还有一个点也很说明问题：如果 continuation 过程中模型调用了 `request_user_input` ，也就是它在等用户做选择，系统不会再额外开一个新的 goal continuation。

这就很真实。

会继续，不等于不会等人。

一个好用的长任务 Agent，不应该像一辆停不下来的车。它应该知道什么时候该往前走，什么时候该靠边等你。

## 五、预算账本：长任务不是跑完才结账

我觉得 `/goal` 另一个很实用的点，是它把 token 和时间记账挂在生命周期事件上。

它不是最后算一次总账。

它在很多边界上记账：

●

turn 开始时记录 token baseline。

●

工具完成后计算 token delta。

●

turn 结束时补最后一笔。

●

用户中断时先记账，再暂停 goal。

●

外部 UI 要改 goal 前，先把当前进度结清。

●

线程恢复后，重新恢复 active goal 的运行时状态。

这里面最容易被忽略的是“外部 UI 改 goal 前先记账”。

比如 Agent 正在执行，用户这时点了暂停或改了 goal。如果不先把当前已经发生的 token 和时间记到旧 goal 上，后面状态一变，这段工作就像没发生过一样。

这就是长任务系统最麻烦的地方：真实世界不是一条直线。用户会打断，UI 会改状态，工具会慢回来，线程会恢复，模型会等待输入。

所以 `/goal` 不是在一个地方做预算，而是在所有容易错位的边界上结账。

预算用完之后，它也没有直接把当前 turn 杀掉。

源码里的测试很明确：budget limit 会 steer active turn without aborting。

也就是系统把 goal 状态改成 `budget_limited` ，然后给当前 turn 注入一段提示：

> 目标已经达到 token 预算。不要再为这个 goal 开始新的实质工作。尽快收尾，总结进展、剩余工作和下一步。

这个处理很细。

预算到了，不是让 Agent 立刻闭嘴，也不是让它继续硬冲。

是让它把桌面收拾干净，把做了什么、还差什么、下一步是什么讲清楚。

长任务需要的不是“永不停止”，而是“停得明白”。

## 六、几个源码细节，说明它不是一个简单命令

为了避免这篇只停留在概念上，我挑几个源码里比较具体的细节。

### 1\. 目标长度限制是 4000 字符

`MAX_THREAD_GOAL_OBJECTIVE_CHARS` 是 4000。

如果用户写太长，TUI 会提示你把长说明放进文件里，然后用 `/goal follow the instructions in docs/goal.md` 这种方式引用。

这个限制很合理。

goal 不应该变成第二个超长 prompt。它应该是目标句柄，详细说明应该放在可维护的文件里。这样目标本身保持短，详细要求又能被 Git 管、被人改、被 Agent 读。

### 2\. Plan mode 会忽略 goal continuation

如果当前是 Plan mode，goal 的自动续跑不会启动。

这个细节也很符合直觉：Plan mode 本来就是让模型先想清楚，不要自己动手。你不能一边说“现在只规划”，一边让 active goal 在后台自己往前跑。

模式之间要有边界，否则用户根本搞不清 Agent 现在到底听哪个规则。

### 3\. 中断会把 active goal 暂停

用户打断一个正在跑的任务时，系统会先把进度记账，然后把 active goal 改成 `paused` 。

这比直接丢掉状态好很多。

打断不是完成，也不是清空。打断的语义更像“先停一下”。下次恢复线程时，如果发现有 paused goal，TUI 还会提示你要不要 resume。

这就是一个好用产品该有的感觉：它理解用户动作背后的协作语义。

### 4\. 完成时会回报预算使用

模型调用 `update_goal` 标记 complete 之前，运行时会先补一次当前 turn 的 token 账。

如果这个 goal 有 token 预算，工具结果里会带一个 completion 预算报告，要求模型把最终预算使用情况告诉用户。

也就是说，完成不是一句“Done”。

完成要结算。

### 5\. 前端状态栏不是装饰

TUI 状态栏会显示：

●

`Pursuing goal (40K / 50K)`

●

`Goal paused (/goal resume)`

●

`Goal unmet (4K / 5K tokens)`

●

`Goal achieved (10h 12m)`

这个东西看起来只是 UI 文案，其实很重要。

长任务最怕用户不知道 Agent 现在处于什么状态。它到底还在追目标？暂停了？预算到了？完成了？如果这些状态只藏在数据库或模型上下文里，用户心智是断的。

状态栏把这件事变成一个一直可见的契约。

## 七、这意味着什么

理解 `/goal` 之后，我有几个很强的感受。

### 1\. 长任务的价值在状态，不在口号

“持续做到完成”这句话本身没什么用。

真正有用的是：

●

目标在哪里？

●

当前状态是什么？

●

花了多少预算？

●

谁能改状态？

●

什么条件下继续？

●

什么条件下停？

●

怎么证明完成？

这些问题回答清楚，Agent 才能稳定做长任务。

否则就是把一个复杂工作流塞给模型，让它靠上下文和自觉硬扛。

### 2\. Agent 自驱不是人格，是系统能力

很多人喜欢说 Agent 要有目标感、责任感、坚持到最后。

这些词可以用来描述体验，但不能用来设计系统。

系统里真正对应这些体验的，是一堆很普通的东西：

●

一张表。

●

四个状态。

●

三个工具。

●

一套事件。

●

两段 prompt。

●

一个状态栏。

这些东西合起来，用户才会感觉 Agent “有目标感”。

不是因为模型突然更像人了，而是因为系统把目标、进度、预算、完成证据都放到了外面。

### 3\. 好的 Harness 会把“模糊协作”变成“明确协议”

长任务里最模糊的地方有三个：

第一，目标到底是什么。

第二，现在到底该不该继续。

第三，什么时候算完成。

`/goal` 分别给了工程答案：

目标是 `objective` ，存在 `thread_goals` 里。

是否继续由状态、模式、队列、active turn、goal\_id 一起决定。

是否完成要做 completion audit，然后调用 `update_goal` 留痕。

这就是 Harness 的价值。

它不是替模型思考，而是把协作边界做清楚。

## 最后

Codex 的 `/goal` 看起来只是一个 slash command，但源码里真正做的是一套长任务 Harness。

它把一句很虚的“继续做到完成”，拆成了可持久化的目标、可枚举的状态、可结算的预算、可审计的完成、可暂停恢复的协作流程。这也是我觉得它很值得写的原因。

很多 Agent 产品都在追求“更自主”。但自主不是让模型更放飞，而是让系统知道：

什么时候该继续。

什么时候该停。

什么时候该问人。

什么时候只是预算到了，但任务还没完成。

什么时候真的完成，可以结账。

代码决定 Agent 能不能跑起来。

`/goal` 这种机制，决定它能不能跑久、跑稳、跑到该停的地方。

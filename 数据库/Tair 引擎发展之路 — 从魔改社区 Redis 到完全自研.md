## 写在前面

本文从集团自研的分布式缓存/存储系统 Tair 的版本演化史着手，以服务端研发的角度讲述 Tair 当前在分布式缓存/内存数据库系统上遇到的一些困难和工程化的解决思路，以及演化过程中的一些经验教训。行文会尽量考虑到各种技术背景的同学，尽量用通（geng）俗（jie）易（di）懂（qi）的技术词汇表述。如有描述不够清晰的地方或者谬误，烦请大家指正。另外本文涉及到一些内部的实现细节，还请大家注意数据安全。

这篇文章是技术视角写的，产品视角可以移步 [《社区动态，和 Tair 对云原生内存数据库的探索》](https://ata.alibaba-inc.com/articles/221376) ，配合阅读效果更好。

## 我们所熟知的 Tair

提到 Tair，集团的同学并不陌生，它几乎是集团所有系统的强依赖。大家最为熟知的 MDB、LDB 存储引擎也是 Tair 1.0 版本最为成熟和在集团内广泛应用的引擎（1.0 已对外开源，但开源的版本较内部比较旧）。

Tair 从 2009 年诞生后的十多年发展历史上，1.0 到 3.0 经过了很多次功能迭代甚至是完整的架构重建。当前集团内仍在大量使用 Tair 1.0/2.0，而 3.0 作为 2.0 的超集，在阿里云大规模售卖有一年多的时间了，也在逐渐取代内部的 2.0 版本。下图详细的说明了Tair 版本演化的过程：

![](e6a4285f-e13d-4b5a-8905-c49eb1632b22.png)

## Tair 1.0（MDB/LDB/RDB）和云 Redis（KVStore）

- Tair 1.0 的 MDB 和 LDB 引擎只有 Key-Value 接口，语法结构更类似 Memcache 服务。它是每年双十一的主力队员，也是交易线四大金刚的强依赖。
- 1.0 曾经有个 RDB 的引擎，这个 RDB 只是在 1.0 的架构上实现了 Redis 的部分数据结构（而且是 Tair 私有接口和协议），不支持数据持久化，是一个纯粹的缓存产品（后来被下线）。
- Tair 1.0 的 MDB 引擎经过包装在阿里云上曾经推出过一个叫做 OCS 的产品，支持 Memcached 的接口和语义。再后来存储底层从 Tair 1.0 MDB 换成了 Redis 社区版，再后来完全被云 Redis 产品取代后 OCS 已经退出了历史舞台。

随着 Redis 本身的不断成熟和用户逐渐增多，Tair 团队开始研发云 Redis 产品并对外售卖，上线售卖后相当火爆，也可以说是随着云数据库发展享受到了第一批互联网发展的红利。

云 Redis 的老用户可能知道 KVStore 这个看起来和 Redis 不相关的名字，并且现在还有同学在混淆。这是因为一开始 Redis 原作者不允许云厂商的产品带有 Redis 字样，阿里云 KVStore 完全等价于阿里云 Redis 产品。

## Tair 2.0 (RDB 2.0)

在 RDB 2.0 发布前，集团用户也在尝试使用 Redis 社区版本，但 Tair 团队在集团落地时发现 Redis 社区版本实在不能做企业级的使用，主要的原因如下：

- 集团内用户尤其是电商系，已经发展到非常大的规模。Redis 在大规模集群下无论是基础的集群能力还是稳定性能力都比较差（原因后续分析单线程模型的时候会细讲）。
- 成本的要求：KVStore 集群版是含 Proxy 的，而 Proxy 节点在大集群的成本上占比非常高，还不包括数据透传产生的时延（Tair 一次 RTT 访问大都在 1ms 以下，引擎内只有 0.x 毫秒；通过 Proxy Bridge 后 RTT 增大30%以后。直接映射为架构成本）；Proxy 是为公有云客户的兼容性开发的，而集团内集群访问模式兼容单实例不是必选项（集团一开始购买的就是集群模式，不存在从单节点升级集群的步骤）。
- 集团环境包括 2017 年开始的优酷中间件改造，都强依赖单元化环境。Tair 1.0 是支持多活和同步的，而 Redis 不支持。
- Redis 的抗冲击，抗热点能力很差，集团经过大规模改造后都使用小 Docker，导致连接数暴涨。而社区 Redis 到几千链接就很不稳定，1w 活跃连接后性能开始明显衰退（单线程C10K问题）。
- 内部应用需要更多的数据结构，很多 RDB 2.0 的数据结构都是围绕着用户需求开发的。
- 淘系的全异步化改造，Redis 当时的主流客户端基本没有可靠异步化能力（Lettuce 现在很成熟了，即将对集团发布支持鹰眼埋点和内部数据结构接口的版本）。

所以 Tair 分为了 2 个团队，一个在阿里云负责 Redis 云产品的研发，另一个负责 Tair 1.0/2.0 的集团需求研发。RDB 2.0 主要解决社区版 Redis 和云 KVStore 在大规模企业级场景下应用的问题（上面列出的）。这里不再赘述，文章最后给出了团队其他同事写的一些文章供大家参考（附录1 2 3）。

再后来随着云原生的发展以及组织结构的调整，内部 Tair 2.0 的积累和云上的管控系统整合出 Tair 3.0 版本，同时进行新云产品的售卖（对外称为 Redis 企业版-增强性能型）以及集团内 2.0 版本的升级迁移。在这个过程中，有些团队内进行技术预研的 TairGraph、NVM 存储等等也阶段性取得了一些成果，各自开始占据了相关云产品的一席之地。这些技术也很复杂，本文暂时不涉及，大家可以参考 ATA 其他文章了解。

好了，流水账告一段落，毕竟这篇文章不是在写 Tair 的编年史。附录里给出 2016 ~ 2020 年的 Tair 双十一总结，想了解具体每年演进的同学可以详细了解（附录 4 5 6 7 8）。

### 反思独立引擎和公共“壳”代码

看到这个图，你的第一反应是什么？版本碎片化！对，繁多的版本带来了高昂的开发成本。抛开左边告别了历史舞台的云 Memcached 后，社区版本当下有仍有 4 个存量版本，而企业版的增强性能和持久内存版本分别基于社区 5.0 版本和 6.0 版本独立开发，PDB 又是一个全新的自研架构。这么多版本，做一个新功能要合并多少次代码？每个版本的修改或多或少都有些差异，这就给测试和功能稳定带来了很大的挑战。集团内可以推动升级，可是公有云用户对于大版本升级的抵触是很大的（担心兼容性或其他变更风险）。

社区版本的发展可以跟着 Redis 社区一起演进，一直到 7.0、8.0 等等。 随着内部特性逐渐的合并到社区以及个性化修改不断地 Module 化（Redis 原生的 Module 扩展能力），兼容社区新版本的开发成本逐渐在降低。如果产品上只维护三个版本，复杂度还是基本上可控的。但是企业版本的发展遇到了较大的问题，主要有以下两点：

- 企业版本的自研修改很多，很多特性代码量不低且无法 Module 化（多线程以及 Binlog 跨域同步等等）。
- 如果追随社区版本来发布对应的企业版，需要投入大量精力研发企业版 6.0、企业版 7.0、企业版 8.0… 研发成本很高且每个版本的质量都需要时间去稳定。

如果不追随社区版本，那我们需要一个稳定、健壮、易维护的公共“壳”代码，和各个存储引擎一起发展。那么一开始朴素的想法自然是选择最新的 Redis 社区的最新稳定版本，在这个基础上自研和不断合并社区的上游修改。但是愿望是美好的，现实却是很残酷。企业版的自研修改太多了，和 Redis 社区代码的差异比较大，而 Redis 社区每个大版本的修改也比较大，所以合并上游不是简单的事情（之前列出的特性列表已经能说明复杂度了，追一次大版本超过 10 个人月的研发成本）。

早期的 Redis 社区代码比较清晰易读，但是随着各种复杂功能和“奇怪”能力的引入，社区代码逐渐有复杂度失控的现象。当然“失控”这个词有些重，但是 Redis 社区代码如果用严肃的工业代码标准去审视的话，目前是存在较大缺陷的。有很多开源工具都可以量化代码的复杂度，主要的依据是代码的圈复杂度（比如循环和判断的缩进层数，循环次数）和模块间依赖关系评估（引用的外部变量的数量，能否进行单元测试等等）。下图是 Redis 社区代码的量化复杂度指标：

![](931ee407-97c8-41a4-90d1-49ea5e8d5a5f.png)

当然，这只是表面上的直观评测。如果大家了解过 Redis 的设计的话，会知道 Redis 是一个单线程的架构。主线程以事件驱动的方式处理所有的网络连接事件和定时任务。同时会有一些后台线程（BIO）做一些异步删除数据和异步关闭文件的事情。为什么是单线程？不同的人会讲出来很多不同的原因，但是无外乎以下说法：

- Redis 的操作大都是在内存里，基本上不存在阻塞的操作，单线程事件驱动足够了。
- 单线程实现比较简单，数据结构可以做到无锁，性能会更好。
- 反正集群方案就是水平扩展分片数，性能不足了水平扩容足矣，没必要多线程提升代码复杂度。
- ...

听起来都颇有道理是不是？对于 Redis 集群而言，如果业务机器就永远保持在三五十个以内；连接数始终维持在几千以内；单个数据结构（List、Hash、Set 等）的字段维持在千以内；总体请求维持在单节点三五万以内；而且请求基本上都是简单的 O(1) 或者 O(lgN) 的查询。那这个 Redis 服务确实会很稳定的，可能业务一辈子都不需要更快更好的 Redis 服务了。

但是你也看到了，我加了好多的限定条件。聪明的你一定已经意识到了，如果不满足这些限定条件，Redis 就开始遇到各种各样的问题了。其中有些问题能通过水平扩容解决，有些却不能。为了直观去了解这些问题，我给出一些真实发生在公有云和集团内的问题场景跟大家讨论一下：

- 某用户打满了 Redis 的服务，主线程 CPU 使用率 100% 后业务开始卡顿，为了解决问题，用户紧急在控制台进行扩容。然而 Redis 主线程过于繁忙，新的主备关系很难建立，建立后数据同步进度特别慢。用户特别着急，但我们除了让用户降低流量外束手无策（限流对业务伤害太大，当下只是卡顿，限流会大面积不可用）。最后怎么解决的？说来惭愧，等用户流量自然降低后才升配成功的。
- 某用户的访问存在间歇的峰值，主线程负载时不时飙高，导致管控采集服务监控的请求也时不时超时。最终造成了监控数据的曲线出现断点，引发了用户投诉。为什么超时？因为监控链路和数据链路都是主线程处理的。当前只是在社区版上把探活端口和逻辑移动到了另外的线程，监控和管控仍在主线程。（正在改造，但是还是遇到了很多困难。因为 Redis 单线程，所以数据结构都是线程不安全的。所以在别的线程获取信息要么加锁，要么主线程提前生成好。提前生成看起来挺好是吧？但是主线程执行一个慢查询的时候，也就不会执行生成的定时任务去生成这个信息了，拿到的也是旧的）。
- 读写分离场景下，Redis 链式挂载了多个同步只读节点，从 Master 开始直到最后的只读节点，数据更新同步的一致性逐渐降低（链式逐个同步存在时差）。当 Master 遇到大流量打满 CPU 时，容易造成主从断开（堆积的同步请求太多或者心跳失败），然后触发链式同步断开后逐个节点全量同步。然而 CPU 是打满的，同步断开后更难建立了，最终难以恢复。为什么是链式同步不是星型同步？链式直挂载一个只读节点都会出问题还敢星型啊？我们能做什么？检测到这个情况后 Proxy 隔离数据不同步的从节点。但是！这是读写分离实例啊，流量大到了主从都断开了，隔离了更多的只读节点这是要让系统雪崩吗？
- Redis 作为缓存使用时，为了缓存一致性，数据都是有过期时间兜底的。如果一个节点长期以高 CPU 运行时，过期检查和清理的定时任务就得不到足够多的优先级去执行，累积的过期数据过多后达到内存上限就会淘汰。业务会发现明明存在很多过期数据，但是淘汰的却不一定是过期的数据。
- Redis 的内存统计是进程级别的，没有分区域（数据区，元数据区、Client buf 等等），当遇到了一些网络延迟大或者客户端/服务端处理缓慢的情况时，会造成较多的 Client buf 占用。当内存统计达到设置的阈值后就开始淘汰用户数据了。那为什么不把统计分开？统计各个单独区域有这么难吗？技术上不难，但是这是个繁琐的工作，但凡漏掉一处就会引发大问题。Redis 怎么统计全局的？Redis 内存分配和释放在 malloc 和 free 上包了一层，有自己的 zmalloc/zfree，在申请和释放的时候做的。那 Redis 后台还是有几个 BIO 线程啊，怎么保证统计准确？难道用原子变量？对，就是原子变量，每次内存申请和释放都是原子加减一次。如果再区分每个区域，都包装一个 xxx\_malloc/xxx\_free，先不说繁琐性，原子操作的翻倍会带来性能的进一步降低（原子统计有些按照 Cache Line 对齐的小技巧减少 False Sharing，但是高频原子操作带来的性能损失还是尽量要避免的）。
- 某直播用户，采用 Pub/Sub 机制进行弹幕的广播，需要 1 对 N 的广播能力。但是 Redis 的单线程负担不起（1 对多等于请求放大），最终业务采用了一主几十从的架构去做链式的广播消息推送，这个架构特别复杂且运维难度很高。如果 Redis 能支持1对几十甚至几百的广播能力就不用这么多从节点了。
- ...

好了不列举了，这篇文章不是吐槽大会。你可能觉得上面的场景有些极端。是的，有些是比较极端，但是会出现这些问题的偏偏都是GC6/7的用户以及集团内的大用户（这些用户摸到了 Redis 的能力边界）。这些场景或多或少都和这个单线程的设计有关系，在 Redis 社区版本 6.0 之前的线程模型是这样的：

![](3ac1f4e4-0086-4169-aca2-98609ad27adc.png)

这个主线程以事件驱动的方式处理来自连接的网络读写事件和服务自身的 Cron 定时任务，主要有：

- 处理用户连接的建立和断开以及数据命令的执行（包括用户的数据请求、内部监控的采集、内部管控的运维指令处理）
- 处理数据引擎的定时任务，包括过期数据的清理，内存碎片的检查和整理
- 处理命令的 AOF 持久化、主从同步的数据发送
- 集群的一些定时任务，心跳，信息交换
- 一大堆的状态检查以及相应的回调操作
- ....

单线程成了原罪，用户数据请求跑满 CPU 的情况下连基本的功能都保证不了，更别说一些更高层面的问题了。比如内部管控链路和用户数据链路在一起的话安全性怎么保证？即使内部鉴权能保证安全，但是传统行业的一些企业级准入规范能允许这样的设计吗？。

做出这个改动的依据是什么？或者说怎么判断这样改能提升性能的？当然是 Profiling 结果了（一切没有预先 Profiling 的性能优化都是耍流氓）。Redis 最常见的 O(1) 场景的数据获取命令跑满时，在火焰图里是这样的：

![](244093cf-ddd7-480c-84fa-5fd88738997b.png)

很直观吧？因为命令处理的高效，普通的读请求耗时最大的地方在网络读写上。这也是 Redis 6.0 这么改造的原因。这么改确实也很简单，读写命令分发出去的时候，主线程是等待的，所以没有数据上的竞态条件，也就不需要对数据区域加锁。但是缺点也很明显：

1. 连接还是都维持在一个线程上的，没有办法增大连接数，而一万个活跃连接以上后 Redis 性能开始衰减
2. 主线程有等待的“堵点”，这时候CPU是闲着等待的，造成了资源浪费
3. 数据命令还是单线程执行的，所以单个线程的数据处理能力会限制最大的吞吐，此时再增加线程数无法提升

第3个原因有 Redis 自己设计的复杂性在里面，社区也是暂时放弃了第3条路（改造引擎多线程太难了，需要从低到高的整体重构）。而前2条我们是能解决的，阿里云对外售卖的 Redis 企业版-性能增强型的模型是这样的：

![](8b5c3156-e1ff-477c-adc3-cc69d6230b12.png)

差别是什么？我们的 IO 线程自己来管理 Client 了，这就可以通过增大 IO 线程数的方式来水平扩展大连接数能力。受益于完全的流水线设计，可以消除主线程的“堵点”，加之 IO 线程承担了之前主线程的网络事件处理，企业版 Redis 的性能得到了进一步的提升（但瓶颈依旧是单线程的数据引擎处理能力）。如果 Redis 的数据请求都像 HTTP/1.1 一样，客户端与客户端之间没有直接的关系，这样的设计就很美好了。但是并不是，Redis 有诸如 blpop 这种数据不存在则 block 住客户端，直到数据有再返回的命令，也有 client kill 这样的关闭指定连接的命令。这些复杂行为的命令导致了连接与连接之间存在有一些操作，就必须考虑并发安全的问题。但是 Redis 的代码复杂性导致了这个并发安全很难做，需要大面积重构（无脑加锁就跟高性能说再见了）。最终的设计方案比较简单，一旦有客户端执行这些交互命令，就把这个客户端交给主线程去持有了，IO 线程就不再持有。通过这样的方式实现没有数据争用。代码流程上是清晰了，但是如果所有客户端都是在执行复杂命令，那么这个多线程加速就名存实亡了。但毕竟使用这些阻塞命令的场景很少，所以实际运营中也没有发现性能衰减到单线程的问题。

尽管这个流水线看上去很复杂，实际上被单独抽象出来了，针对社区版最核心的修改还不到千行。这个修改解决了集团内动辄数万连接数的大应用上云问题以及云上使用连接池的大客户的连接数问题。但是并没有解决上面提到的那些真真切切的痛点（命令和定时任务还是单线程在处理）。

客户选择 Redis，自然对 Redis 社区版本的能力和边界有过了解和预期。所以上面那些极端场景尽管作为技术人员觉得脸上无光，但是解释清楚后客户基本上都表示能理解和接受的。但是，既然是“企业版”，“企业”这个词体现在哪里？是大连接数抗冲击能力？是更丰富的数据结构去覆盖更多的场景？是更好的性能和热点数据访问能力？是精确到秒级的数据回滚能力？是全球多实例分布式同步能力？还是实时大 key 和热点 key 展示能力？

是的，这些能力是我们的优势，也能称之为企业级别的能力。但是，Tair 就止步于此了么？不，我们的目标是星辰大海（这句划掉）。Tair 对用户的核心价值，就是快，好用，时延稳定。Tair 的定位是在线场景的实时数据引擎（区别于离线场景，但不代表离线不能用）。既然上文花了很大的篇幅去讲现状以及存在的问题，那自然是要有更好的解决方案的。

除了那些缺陷还会有一些用户需求。我们知道 Redis 的数据是全量存储于内存中的，当用户的数据规模到了一定程度后，用户是希望有更便宜的存储介质的。几家友商（包括阿里云自己）都曾经推出过名为“冷热分离”的 Redis 存储。阿里云的冷热分离产品内部叫 Amber，是在 Redis 代码基础上改出来的。一开始运行的是挺好的，但是用户往往会有一些 big key 存在，当这些 big key 经历了从冷到热后，就需要从磁盘介质换入内存中。但是因为 Redis 本身的单线程逻辑，越大的 key 卡顿时间就越久，这样对用户的使用体验就很差。最后 Amber 这个产品难以解决这些顽疾，最终还是下线了。环顾友商，要么下线了此类产品，要么是苦苦挣扎着，要么只支持 KV 的冷热分离以规避 big key 等坑。

其实像 1.0 的 LDB 那样，直接基于 RocksDB （Tair 1.0 的 LDB 基于 LevelDB，因为当年没得选）设计一个落盘的格式，直接存储在磁盘上就好了。LDB 的经验是当机器的 Page Cache 较大的时候，整体服务性能还是很不错的（MDB 99RT 1 ms 以内，LDB 99RT 2 ms 以内），而且进程内部还可以加一层查询 cache 来满足热数据的高频访问，这就不用设计复杂的冷热交换（当然缺点是冷启动的时候性能还不是最优的）。

好了，这两个需求明确了。那么要解决 Redis 企业版的这些问题，同时要实现更多的存储介质支持，怎么做？低头看路，Redis 的代码难以进行这样的复杂改造。抬头看天，Redis 阻碍了 Tair 迈向内存数据库的路。当前孱弱的代码基础不进行较大重构难以继续发展高级能力（社区在慢慢的重构，但是有待于观察，目前看步子比较慢需要数年持续改进，我们等不了）。

从大环境角度，Redis 的作者 Antirez 隐退之后，Redis 交给“社区”维护。尽管我们一直在努力有更多的社区话语权（1 个 core team member，1 个 committer），但是明显把控社区的依旧是 RedisLabs 这家商业公司。 现在 Redis 的开源主页都开始光明正大的给 RedisLabs 的云产品引流了。如果有一天，Redis 的开源协议修改了怎么办（有前车之鉴）？阿里云 Redis 产品这么大体量要居安思危，未雨绸缪。

从我个人角度，我从 14 年开始维护 Tair 1.0 的服务端，做了很多提升性能、稳定性、可观测性、可运维性的工作。也受限于 1.0 的一些历史包袱和业务兼容要求而无法进行更深层的修改。后来负责 RDB 2.0 的多线程实现，以及功能往 3.0 迁移。总之是 Redis 的代码看了，坑也踩了，客户的骂也挨了（从内部 1.0 客户到云上 3.0 的海量客户群）。当然内部客户自己不占理时不一定“骂”的赢（这句划掉）。这些累计的经验能满足从头设计一个兼容 Redis 的多线程 NoSQL 的技术要求了。正好去年疫情期间居家办公不能外出，闲的时间就一直在构思这个东西怎么设计，最终花了个把月完成了原型设计后验证想法可行。和主管讨论后开始立项去做新架构这个事情。这个新项目的内部代号是 Tair v4，即 Tair 4.0 版本。经过一年的工作，PDB 作为Tair 4.0 的第一个支持的引擎正式上线并在阿里云售卖（PDB 对外叫 Redis 企业版-容量存储型）。

## Tair 4.0 的设计与实现

存储系统的代码设计一定要认真，实现上一定要细心。大型项目到了开发阶段首先要控制的就是代码复杂度。开发阶段产品复杂度是不变的，因为当下的需求是确定的。而代码复杂度是由设计复杂度和实现复杂度共同影响的。好的设计应该对当前的需求有足够的抽象性，同时对未来的演化有一定的前瞻性。Redis 的代码是 C 写的，有些缺乏OO的设计思想（这两者没有关联关系，不是语言问题，不是语言问题，不是语言问题，OO 的设计和语言没关系）。要支持多样的存储介质，首先就是抽象的引擎接口，然后每种介质上分别实现自己的数据操作。另外 Redis 内部每种数据类型支持多种实现，比如 Hash 支持 ziplist 和 hash 两种编码，前者是线性表实现的压缩格式（极限时间换空间）。而且存在超出阈值提升的逻辑需要在内部包装并隔离掉区别（毕竟没有什么问题不能通过增加一个间接的中间层来解决）。作为内存存储，用户对于内存容量很敏感，需要调整结构体对齐（甚至考虑内存分配器的slab大小）来获得性能和存储的平衡。社区版本支持的编码和格式如图所示：

![](552dff93-0723-4a15-9e7e-96c3ea6423ba.png)

Tair 1.0 的网络框架是 libeasy，这个框架封装了标准的一问一答式的服务流程，很适合快速实现一个类似的服务且性能不俗。但是 Redis 的不少接口语义是要求服务端主动推送的，而且 libeasy 的 C 语言框架和 4.0 主体的 C++ 11/14/17 较难合作，比如智能指针总不能 new 出来存成 void \* 吧（行倒是行，有点难维护）。最终还是拿现代的开源网络库整体洗了一下加了一些需要的特性进去作为基础库。时序图如下：

当然每个部分都是可以配置的，支持单个 IO、多个 IO、多个 IO+ThreadPool 等多种模式。因为引擎特性的不同，配置成最适合的 IO 模型才能获得最大的吞吐和更好的时延控制。这里多说几句，很多人不觉得 IO 模型是个很复杂的东西，因为常见的模型无非就这几种。但是实际上在 IO 到 ThreadPool 的任务投递上就有很多种不同的写法，要维持服务稳定的时延需要针对具体的引擎特性选择更合适的策略。

涉及到各个模块的实现有很多细节没法逐一展开说，我挑选几个代表性的说一下吧。首先是协议的编解码，Redis 社区版本没有抽象出专门的 Encode/Decode 接口，Request 是一个代码入口，而 Response 却有很多出口，所以给社区版本适配二进制协议栈很困难。而且 Redis 原生的协议是一个 Json 的 DOM 格式，Request/Response 只有里也只有数据，没有 sequence，更没有预留任何的扩展字段。Tair 4.0 在设计上直接抽象出协议编解码部分，首先兼容了 Redis 原生协议，然后可以很方便的适配多种格式的协议（私有二进制、Memcached协议、Tair 1.0 协议等等）。

前文提到了 pubsub 这个广播机制，到了 Tair 4.0，当服务以完全的多线程模式运行的时候，subscribe 的连接是分布在各个 IO 线程的，而 publish 请求是发送到其中一个 IO 线程的，这就需要接收到该请求的 IO 线程将要 publish 的消息推送到其他的 IO 线程去让各线程自己发送以起到并行加速的效果。 这个实现的原理图是这样：

![](5bee8243-c461-41bd-ac8f-7a1a8760982d.png)

但是，这个命令的返回值是接收到推送的客户端数量，这就需要推送线程要关心处理结果，但是这个等待和合并执行结果的操作必须是异步的，不能阻塞等待。这就要求网络和命令处理框架要支持拆分、投递、聚合命令，需要实现一个线程安全的委托机制。感谢 std::bind/std::function 构造的闭包，感谢 std::shared\_ptr 管理资源不用考虑谁来释放内存。

最终的推送能力提升了略小于 N 倍（N 是 IO 线程数）。因为 publish 线程本身处理的推送数量减少到 1/N，但是线程间任务分发消耗使得性能只能逼近 N 倍而到不了 N 倍。

然后是统计，多线程高并发服务的统计设计上都不用想，必须是 ThreadLocal + 异步线程合并。原子变量？动辄十几个线程跑起来，一些核心指标的统计次数是很多的，原子操作想都别想。用这个方式就是读的线程累一点，需要把每个局部都读一下加起来（脏读就行，一般意义上的统计无需考虑绝对的原子性），异步线程按照统计周期去做合并和计算即可，获取统计的时候不需要计算。

![](52125fe0-9b24-4870-992c-003e7b1bdccd.png)

内存有统计、网络有统计、服务层也有统计，这些计算和合并大同小异，当然是用类模板+宏函数来写好统一的，其他地方定义一下统计项的名字、类型（秒级、总量、历史最大、平均）直接就能用了（前文说了，代码不能跨模块，统计也不行）。DRY，这是基本原则。4.0 支持的统计项比 Redis 自身细很多，尤其有了数据区域的精确大小甚至区分了数据和索引大小后，淘汰判断再也不是问题，异步的过期逐出线程也不会因为服务忙而中断。窥一斑而知全豹，下面给一张全量的接口时延直方图（原始数据）作为示例：

那内存统计怎么做的？这个说起来比较复杂，Redis 可以用自己的 zmalloc/zfree，甚至修改所有依赖的三方库的内存分配。但这个在 C++ 上比较困难，一来是用了蛮多二方三方库，有些不支持替换默认的内存分配接口，二来是很多对象都是 STL，还得重载 operator new() 和给 STL 实现额外的 Allocator 类。在使用诸如 Jemalloc 的库时可以直接在覆盖的 malloc 上（glibc 的 malloc 是弱符号能直接被用户代码的 malloc 替代）调用 Jemalloc 的函数，但是使用 glibc 的 malloc 时，需要在我们覆盖实现的 malloc 中继续调用 glibc 的 malloc，有点绕是吧？4.0 的代码还是同时兼容 macOS 和 Linux 的，需要做一些兼容处理。最后实现的 hook 函数有点复杂，其中最复杂的 calloc 如下图所示：

接下来是过载保护。一旦用户真的触及到了数据库服务的边界，服务要有足够的自保能力。或者换句话说，当请求大于数据库的承载能力时，不宕机是数据库最后的体面（随便你怎么干掉用户连接，前提是精准发现和结束）。过载保护详细说得专门写一篇文章去讲，简单说就是最大文件数、最大连接数、系统负载、连接过期、连接读写内存、指定地址最大连接数、流量、QPS、黑白名单等内容的监控和处理。服务的毛刺是因为某处存在阻塞或者高耗时的操作而引起的，而排队会使得毛刺蔓延。在系统满载的情况下，这是雪崩的触发条件。在最后一根稻草压垮骆驼前骆驼是有些征兆的，骆驼不可能像原子跃迁一样从生龙活虎直接到死气无力。但是在异步系统雪崩前，系统的各项指标恶化的不会特别明显。具体原因要引入排队论来讨论，有机会另开贴讲吧。

得益于设计上的抽象，存储引擎的差异被隔离了，最终 Tair 4.0 的 PDB 和 RDB 都可以直接互为主备运行。但是因为磁盘存储的特殊性，有些内存数据结构暂无磁盘版本，所以不能直接这样部署。但是当前能给 PDB 直接挂载 RDB 的只读从节点，这样可以用于更换存储引擎的变配或者某些场景下把数据载入 RDB 进行加速读取。

## 代价系统与任务调度

IO 模型看上去很简单是吧？其实这个东西一点都不简单。如何控制服务可能的抖动不是一件简单的事情，也不是几句话能说清楚的。Redis 的数据结构太灵活了，相关的操作命令也很多。甚至很多都是原作者一时兴起加上去的，比如 keys \* 这种模糊查询命令（类似 MySQL 的 LIKE ）就是噩梦。Redis 作为一个 Hash 存储引擎如何处理这样的模糊查询？有某种索引？想多了，就是 for in all kv，逐个匹配，数据量越大这个操作越没救的。

Redis 的命令从时间复杂度上分类大概有 O(1)，O(lgN)，O(XlgN)、O(N)、O(M\*N) 等等。我们在算法分析的时候往往会忽略常数。但是，工程上是不能忽略常数的。仅凭一个 O(N) 或者 O(lgN) 是无法判断哪个命令执行更耗时的，需要去联合数据区域的预查询来综合判断执行的时间复杂度。

有了代价系统才能有快慢分离，才能更好的隔离慢查询使偶发的慢查不至于影响到其他没有数据依赖的查询。Tair 1.0 是单纯的 KV 存储，很容易判断复杂度并对请求进行快慢隔离（命令操作的 key 数量就是依据）。而 4.0 要建立更复杂更高级的代价估计系统才可以，另外还需要以任务调度来实现把偶发的慢查收敛到一起，保证正常请求尽快返回，给用户更好的顺滑体验。

Redis 社区为什么做不了？当前就是个单线程引擎啊，就是识别出来了慢查询又能咋地？老老实实改业务代码去吧。

不估计代价能不能做？有别的办法吗？有！有可靠的用户态抢占式协程实现也可以，用时间片的思路来管理每个请求执行，配合事务并发控制，也能做到。怎么实现可靠的用户态抢占式协程？是改造编译器在固定的指令后插入调度点吗？还是用现成支持这个的语言比如 erlang 来做？要不要一起来研究下？欢！迎！转！岗！

代价系统和任务调度在解决什么？在解决进程内部资源的隔离和分配。从 VM 到 Docker，隔离度从物理机上的多个系统到了一个系统内的多个进程，现在终于要到进程内部了。既然没有前车之鉴，那就自己走着看吧。有了这个，就有了ServerLess 的基础了，小用户合并到一个集群里去就有了技术支持了（没有隔离好资源的话，让用户相互伤害吗？）。

## 内存数据库最好的形态是什么

这一段纯粹是个人看法，纯粹天马行空，权当头脑风暴供大家一乐。

Redis 为什么要有 Lua Scirpts 呢？因为数据 API 不够灵活，无法覆盖更多的场景和语义。Redis 的 Lua 就是 DSL，但是这个 DSL 只有数据操作（DML）语义，没有数据定义（DDL）语义；而且是命令式的，不是声明式的。如果支持了 DDL 呢？最具有表达力的 NoSQL 的数据模型是什么呢？我觉得是对象模型，比如支持二进制的 Json 存储（MongoDB 笑了）。Redis 企业版有个叫 TairDoc 的扩展数据结构，直接映射用户代码里的一个 Object 结构。如果 Doc 支持引用另一个 Doc，就像代码里指针可以指向别的对象，那么就有了无限种数据结构和算法了（一个类似于存储过程的 DSL 操作数据结构实现算法）。我们为什么需要数据库，因为要持久化，要把所有应用访问的数据存到一个公共的地方去。为什么我们需要愚蠢的 ORM 映射，代码里的对象能直接持久化和便捷的访问某一个字段不好吗？如果这些字段的修改以及关联对象能在数据库内部以“算法”的形式直接修改好，何必像现在这样读出来修改完再写回去？

曾经的持久化存储设计经历了很多种模型的百家争鸣时代，最终关系模型取得了事实上的碾压。关系模型在实现复杂度和使用复杂度上做到了平衡。这也受限于在存储介质上实现持久化的复杂度。而且固定的模型才能对查询做很多范式化和优化。但是内存数据库其实不是一个“实时”持久化到磁盘的系统，大都是基于定时的 CheckPoint + 增量的 Binlog 日志来实现数据一致性的（不一定呦，NVM 成熟了）。数据可靠性并未降低，只是故障恢复的时间久一点。那基于这样的模型，其实可以尝试更有意思的思路来做内存数据库，而不是把关系模型的当前针对持久化介质存储特性的实现直接从磁盘上搬到内存里。我的经验告诉我，介质读写速度不是影响某种模型性能的最大因素。比如把 RocksDB 从磁盘文件系统放到内存文件系统里，能快一个数量级吗？并不会，因为最大的开销不在 IO 上，而在为了适应持久化介质所做的流程设计上、在具体的归并排序上、在内存随机格式和磁盘顺序格式的编解码转换上（为什么这么肯定？除了理论依据，Tair 真的试验过也尝试过。纸上得来终觉浅，绝知此事要躬行）。当然，不是说内存数据库不能是关系型，而是关系型要针对内存的存储特性进行流程和存取上新的设计。

# TDDL 分库分表键缺失导致的 1024 倍写放大事故复盘

## 一、现象

2026-10-14 20:02，皮肤广场渲染洪峰期间，任务表 `vip_activity_reward_record`（TDDL 逻辑表，8 库 × 128 表，分片键 `reward_user_id`）的**写 QPS 瞬时冲到约 80 万**，而模块渲染本身的峰值只有千级 QPS——写流量是业务量的几百倍，DB 侧先于业务告警。

## 二、定位过程

### 1. 中间件侧的"静默"陷阱

这类问题最反直觉的地方在于：除了 QPS 监控爆表，**所有常规告警全部静默**：

- errors: 0 —— 广播出的 1023 条语句都是合法 SQL，只是更新了 0 行
- 单条 RT ≈ 0ms —— 0 行更新的亚毫秒语句不触发慢 SQL
- 连接池 active 远未打满
- tddl-stat 的写:读 QPS = 52:6（约 10:1）—— 正常业务表应该读多于写，**写读比倒挂是这类事故最显眼的指纹**

结论：排查"数据库被写爆"但错误日志干干净净时，先看写读比。

### 2. 调用链定位（EagleEye）

从鹰眼 trace（705f002817919803990723864e）逐层展开，拿到完整触发链路：

```
IpSkinTaskModuleProcessor.exposedTask          :223   皮肤抽奖模块曝光任务
└─ ActivityTaskManager.exposedTasks            :297
   └─ ActivityTaskManager.initTask             :415   INSERT（正确路由）
      └─ (L422 autoFinished：曝光即完结)
      └─ ActivityTaskManager.execute           :430
         └─ TaskEngine → AbstractTaskProcessor.execute :62
            └─ AbstractTaskProcessor.postProcess :231
               └─ ActivityTaskRecordManager.updateTaskRewardRecord :159
                  └─ ActivityRewardRepository.updateActivityRewardRecord :116
                     └─ VipActivityRewardRecordDAO.updateByPrimaryKeyWithBLOBs
                        └─ vip_activity_reward_record.xml:480
                           UPDATE ... WHERE id = #id#    ← 缺 reward_user_id
```

### 3. span 截断的误导

一次渲染的 trace 里只能看到 **481 条 TDDL_UPDATE span**（8 库 × 60±1），"一条 trace 更新 60 多次"曾一度被当成线索。实际上这是 **span 数量上限（1050）截断**后的可见切片：正常路由一次只该有 1 条，481 条是广播被截断后的部分视图，按时间窗外推 ≈ 1024 条。链路追踪工具的展示上限，会系统性低估爆炸半径。

### 4. 根因

`vip_activity_reward_record` 以 `reward_user_id` 为分库分表键，且 `allowFullTableScan=true`。该 UPDATE 的 WHERE 只有主键 `id`：

- TDDL 将 1 条逻辑 UPDATE **广播为 1024 条物理语句**（8 库 × 128 表），其中 1023 条更新 0 行
- 关键澄清：`reward_user_id` 在 Java 层一直有值（Repository 层还有 `checkNotNull(record.getRewardUserId())` 校验），**是 SQL 模板里根本没写它**——DAO 参数校验 ≠ SQL 用上了分片键

触发面：autoFinished 任务"曝光即完结"，新用户首曝渲染时一次会触发 2 个此类任务、各广播一次；峰值分钟渲染从 ~400/min 冲到 34904/min（秒级 2300/s），首曝占比约 27%。

## 三、证据链（多源交叉验证）

单一证据都可能有歧义，这起事故最终靠四路独立证据收敛：

**SLS 聚合日志**：事故峰值分钟 19396 次更新调用，99.86% cost ≥ 100ms——这是广播的耗时签名（正常单表路由 1~3ms）。

**行级铁证（生产物理库直查）**：取事故窗口一条记录，`version = 1`、`gmt_create == gmt_modified`，证明插入后恰好被更新一次；而广播的 1024 条语句中只有这 1 条真实生效。

**分钟级量化**：事故分钟内单张物理表仅 64 行 `gmt_modified` 落在窗口内（含 INSERT），而同分钟该表被执行的 UPDATE 约 1.9 万条——>99.6% 是 0 行空扫。

**系统计数器**：实例 `Com_update` 计数 30 亿+ 且持续增长，常态均速约 127 条/秒 UPDATE，写:读 ≈ 6.5:1——广播底噪在数据库计数器上留下了两年的指纹（提示：该缺陷造成的底噪一直在，只是当天被洪峰放大到爆点）。

**binlog 角度**：ROW 格式下 0 行影响不产生 binlog 事件，所以 binlog 行变更数:语句数 ≈ 1:1024，放大倍数本身就写在 binlog 里。

**物理 SQL 溯源技巧**：TDDL 会给每条物理 SQL 注入 `/* traceId/rpcId */` 注释——traceId 前 8 位 hex 可还原来源 IP，中段 13 位十进制是请求发起的 epoch 毫秒。据此可以从 SQL 洞察里把一次请求发出的全部 1024 条物理语句捞出来，逐条对应分表后缀。

## 四、临时止血：限流调整

修复发布前，先把皮肤抽奖模块的渲染限流从**单机限流调整为集群限流**，把洪峰流量挡在模块入口，压缩广播触发面，预发验证通过后先行上线。

## 五、修复与验证

### 修复（一行）

`vip_activity_reward_record.xml` 的 `updateByPrimaryKeyWithBLOBs`（L480）WHERE 补上分片键：

```xml
where id = #id:BIGINT# and reward_user_id = #rewardUserId:BIGINT#
```

### 预发验证（前后 trace 对比）

- 修复前（复现）：新用户首次进入频道触发曝光任务，更新任务状态时广播更新所有分表
- 修复后：同样的曝光链路不再广播，单次首曝渲染的物理 SQL 从约 2050 条降到 8 条

## 六、git 考古与同库审计

追历史发现这个坑埋了三年：

- 文件初版（2023-03）的四条 byPrimary 语句 **WHERE 全部只有裸 id**
- 2024-07 有一个只改一行的提交，手工给 `updateByPrimaryKeySelective` 补了分片键——恰好是当年唯一被业务用到的 UPDATE
- 事故语句 `updateByPrimaryKeyWithBLOBs` 是当年漏掉的三条之一，后来被新链路（皮肤曝光任务）首次大规模调用，坑被引爆

同库其余分表表的同类审计结论：另一张表的裸 id UPDATE 属于零调用死代码；其余裸 id 均为 select/delete 且为死语句或低频后台调用。

## 七、修复后的收尾：死代码加废弃标记

事故修复 MR 评审时，评审人指出：**另一条同样裸 id 的 `updateByPrimaryKey` 没改，看着没有代码用到，建议加废弃注解**，防止将来有人启用再踩一遍。

据此做了全量核对：

| 语句 | WHERE | 主代码调用方 | 处理 |
|------|------|------|------|
| `updateByPrimaryKeyWithBLOBs` | 裸 id | 有（事故链路） | 补分片键（本次修复） |
| `updateByPrimaryKeySelective` | id + reward_user_id | 有 | 正确范本（2024 年已修） |
| `updateByPrimaryKey` | 裸 id | 零调用（仅单测） | `@Deprecated` + xml 废弃注释 |
| `selectByPrimaryKey` | 裸 id | 零调用（仅单测） | `@Deprecated` + xml 废弃注释 |

注释只陈述技术事实（"WHERE 缺分库分表键，UPDATE 会被广播为 1024 条物理语句造成写放大"）并指向正确范本，不引用具体事故。动态 WHERE 的 Param 系方法主代码也零调用，但其 WHERE 由运行时构造，不在硬编码缺键范围内。

## 八、经验总结

1. **分表表的 byPrimary 模板必须带分片键**。`allowFullTableScan=true` 的语义是"允许广播"而不是"广播没问题"——它把本该是启动失败的错误静默成了性能炸弹。
2. **看 WHERE，不要看 Java**。`checkNotNull(rewardUserId)` 只保证 DO 里有值；分片路由看的是 SQL 模板的 WHERE 列。参数校验通过和分片键生效是两件事。
3. **中间件"静默"清单**：errors=0、慢 SQL=0、连接池空闲，同时 QPS 爆表 + 写读比倒挂——优先怀疑全表广播。
4. **链路追踪有 span 上限**，一次 trace 里的语句数是截断视图，需要按时间窗外推真实规模。
5. **修复时顺手审计同族语句**：生成器（MyBatis Generator）产出的 byPrimary 四兄弟往往同病，只修事故那一条等于把剩下三颗雷留给下一个调用方；没人用的就加 `@Deprecated` 圈死。
6. **写读比是分表广播的长效指纹**：底噪会持续累积在 `Com_update` 计数器上，日常巡检就能发现，不必等到洪峰引爆。

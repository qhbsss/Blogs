对于开发同学，尤其是对于一线的开发同学来说，对于应用部署几乎就是家常便饭了，打开Aone、找到自己的应用和分支，点击提交部署，然后接上一杯茶就可以静静地等待应用部署完成了，整个过程丝滑地不能再丝滑。不过，有一说一Aone确实是我用过的非常好的集成部署发布平台了，不过也正是这种优秀的CICD集成部署平台，也让我们忽略了真正一个应用部署有多么的复杂。前一段时间在系统地学习和总结线上问题排查和性能优化相关的内容时，让我意识到当前的应用运维和刚入行那些年已经发生了翻天覆地的变化，所以我做了一些系统地学习，然后尝试从应用开发的视角来总结一下容器和虚拟化技术，回答我一直以来的几点疑问：

1. 关于一些基础概念的理解，云原生、虚拟机、容器、Docker、K8S。
2. 容器化的本质是什么？
3. CPU、内存、网络和磁盘如何做资源隔离的？
4. K8S主要解决了什么问题？
5. 一次应用部署的整个流程是怎样的？

## 从应用部署开始说起

记得在14年刚入行时，我主要是从事toG的开源大数据中间件的运维和应用开发工作，那时候基本上国内也都还是刚开始流行结构化、非结构化的大数据存储、清洗、计算和数仓的搭建，在这个过程中最痛苦的事情其实是准备环境，包括创建虚机、配置网络、上传应用包、启动应用。尤其是创建虚拟机，每次应用部署都要和我们几个搞运维的小伙伴用盗版的vmvare做虚拟分配，如果是客户现场还需要跑到机房里去做这些事，状态基本就是这样的：

![](<../images/redirect_71.png>)

机房中风扇声+汗臭味混杂别提多么酸爽了，每次部署光虚机分配就要搞个两三天，那时候我们甚至还没有用上jenkins。生产基本上都是刀耕火种的作业模式，应用打包配置、部署、调试，基本小半个月就过去了，而且每次都是虚拟机分配了又不一定能用，能用了网络又不一定通，网络通了应用又不一定起得来，再加上自己原生的菜鸡属性，每次都搞得晕头转向的。

为了解决虚机资源利用率和部署效率问题，同时也是拥抱云计算的浪潮，原本经常和我部署虚机的运维小伙伴也被调去做openstack + kvm的私有云解决方案去了。不过这玩意实在太新、落地实在太慢，最开始部署openstack的时候都搞了一个月，更别说用了。

更悲剧的是后面Docker开源了，行业内都意识到了Docker的优点，它实在太轻了，所以又转头去拥抱Docker。值得庆幸的是我在这家公司离职之前终于用上了Docker，再也不用去操作那个盗版的vmware了，不幸的是后面专注做业务开发了，和容器、虚拟机暂时说了拜拜，也导致有些断层式的认知缺陷。

说了这么多，其实想表达的是虚拟化其实是一直存在的，vmware是这方面商业化的先驱。我们使用的系统并不是像我们的PC一样所见即所得，基本上都是运行在虚拟机上的，而且早期这种资源分配和应用集成成本异常的高。不过随着云计算的浪潮席卷而来，再加上各种开源解决方案(Docker、K8S、KVM等等)的开源和高速发展，基础资源的分配、使用，甚至应用的持续交付的难度越来越低。不过这也导致"运维"这个岗位基本绝迹于江湖，运维老哥们纷纷转行做云基础底座的开发去了。

## 云原生

## 定义

谈到虚拟化、容器化，它们总是和另外一个概念一起出现，就是云原生。前几年云原生这个概念一直在诸多高P的嘴里流传，我听得也是云里雾里的，不明白到底是什么意思，也不清楚云原生和容器化、虚拟化的关系是什么，这个概念一直在我脑海中都是非常模糊的。

后来系统地了解过才知道，关于云原生每个厂商都有不同的定义，而且这个定义还挺抽象的。这里引用CNCF（Cloud Native Computing Foundation）的对云原生的定义：

> Cloud native practices empower organizations to develop, build, and deploy workloads in computing environments (public, private, hybrid cloud) to meet their organizational needs at scale in a programmatic and repeatable manner. It is characterized by loosely coupled systems that interoperate in a manner that is secure, resilient, manageable, sustainable, and observable.
> Cloud native technologies and architectures typically consist of some combination of containers, service meshes, multi-tenancy, microservices, immutable infrastructure, serverless, and declarative APIs — this list is non-exhaustive.

> 云原生技术有利于各组织在公有云、私有云和混合云等新型动态环境中，构建和运行可弹性扩展的应用。云原生的代表技术包括容器、服务网格、微服务、不可变基础设施和声明式API。这些技术能够构建容错性好、易于管理和便于观察的松耦合系统。结合可靠的自动化手段，云原生技术使工程师能够轻松地对系统作出频繁和可预测的重大变更。云原生计算基金会（CNCF）致力于培育和维护一个厂商中立的开源生态系统，来推广云原生技术。我们通过将最前沿的模式民主化，让这些创新为大众所用。

简单一点的说法：

**云原生是充分利用云计算的优势，从而在云计算中构建、部署和管理现代应用程序的软件方法。**

## 云原生技术栈

对于云原生基座的落地当前最主流的方案是围绕着K8S展开的，主要核心的技术栈大概分下面几部分：

**容器运行时：** 通过抽象计算层资源来实现计算资源的隔离和管控，具体实现使用Linux namespace、cgroup实现。

**容器存储：** 通过抽象存储服务为容器和微服务提供高可用、高弹性和高性能的存储服务，具体的解决方案主要有Ceph、Amazon S3和Rook等。

**容器网络：** 通过将物理网络抽象成一个统一的网络视图，屏蔽底层网络复杂度，以实现容器之间、容器物理机之间的互访，具体的解决方案主要有CNI、Flannel和Istio等。

**容器编排：** 使用容器运行时、容器存储和容器网络的接口和物理设备进行打通，结合编排规则进行容器全局的监控、管理和调度。最主流方案就是K8S。

ps：云原生技术栈这个命题实在太大，涵盖了整个软件设计、开发、交付和实施全生命周期的技术栈，上面也主要是总结了基础底座相关，鉴于水平有限，只能进行粗浅的理解。

## 从物理机到虚拟化再到容器

既然云原生的一部分核心是为了解决基础环境的问题，那我们还是先从基础的概念入手来了解一下通常我们进行应用部署的"底座"。也就是物理机、虚拟机和容器，这将帮助我们对底层的实现有一个宏观的了解。

## 物理机

![刀片服务器](<../images/redirect_72.png>)

物理机通常指我们我们使用的服务器实体硬件，比如上面的刀片式的服务器和机柜。从主板布局上看和家用PC的布局完全不一样，对于服务器的物理机拥有更多的CPU、内存、磁盘和网络带宽。当然我们也会在物理机上安装一个操作系统，以便于可以运行我们的应用程序。但是我们不可能直接在这样一个物理机上部署我们的应用程序，因为那会带来极大的资源浪费。为此我们需要在物理机的基础上创建更多的“子系统”，并在这些子系统中部署我们的应用，这也就是虚拟化技术的最朴素的原理，创建出来的“子系统”我们也称为虚拟机。

## 虚拟化

对于虚拟化技术来说，最朴素的概念就是将计算机的各种实体资源（CPU、内存、存储、网络等）予以抽象和转化出来，并提供分割、重新组合，以达到最大化利用物理资源的目的。

虚拟化技术最早起源于1960年代IBM的虚拟机监视器，最早的虚拟化技术基本集中在学术界，1990年代VMware公司率先将虚拟化技术进行商业化，在Docker、KVM这些技术还没出来之前，vmware系列的产品是我们最常用的虚拟化解决方案了，随着KVM、Xen、Docker等技术的出现，虚拟化解决方案遍地开花，对于虚拟化直接的思路就是引入虚拟层（Hypervisor）对物理资源进行抽象，并在虚拟层上架设对应的虚拟机，也被称为Guest：

![虚拟化](<../images/redirect_73.png>)

### 虚拟化技术的分类

对于虚拟化分类从不同的角度有很多不同的分类，这里主要还是从架构实现上简单做一个分类：

**裸金属虚拟化架构：** 主要是指虚拟层Hypervisor部署在裸机上，并将裸机服务器的硬件资源虚拟化，然后在Hypervisor之上构建OS，比较典型的技术就是VMware ESXi、Microsoft Hyper-V和KVM（Linux内核中实现）等，这种架构被称为Type1虚拟化架构。

**宿主虚拟化架构：** 主要是指虚拟层Hypervisor的实现在宿主机OS之上或OS之中，比较典型的技术就是VMware Workstation、VirtualBox和QEMU等等，这种架构也被称为Type2虚拟化架构。

注：对于虚拟化的分类，有很多种分类方法和视角，具体可以看一下WIKI上的描述，多种复杂的分类对小白不是太友好，因为我们的核心是理解容器，所以只是追求大致能有个清晰的逻辑分类就好了。当然也不是说虚拟化技术不重要，虚拟化技术的隔离性更好（比如ECS就是基于虚拟化技术的），有时候我们的容器甚至也是要部署在虚拟化技术产生的虚拟机中的，只能说不同的技术解决的问题不一样，不可轻易相互比较。

### 举个栗子

以一个小例子简单说明一下Guest OS 、Hypervisor和Host OS是如何做一个数据包发送的：

1. **Guest OS中发起数据包发送** ：在Guest OS中，一些应用（如Web浏览器）需要发送网络数据包。它们通过调用TCP/IP栈（如 send()函数）将数据发送到网络。
2. **Guest OS的网络驱动** ：Guest OS中的网络驱动程序负责处理网络数据包。Guest OS使用虚拟网络设备将数据包封装并准备好发送到Hypervisor。
3. **进入Hypervisor** ：Hypervisor接收到来自Guest OS的请求，并处理发送数据包的操作。
4. **Hypervisor与Host OS的交互** ：Hypervisor将Guest OS中的数据包转发到Host OS的网络堆栈。这个过程可能会涉及修改数据包头（如MAC地址），使其适合Host OS的网络配置，Host OS的网络驱动接收这个数据包，进行进一步处理。
5. **Host OS的网络发送** ：Host OS将数据包发送到其网络接口，经过物理网卡发送到实际的网络（如互联网）。

所以我们可以将Hypervisor看成一个代理的实现，实际上虚拟化体系很复杂，不只是这么简单。上面的例子可能不太严谨，旨在说明虚拟化体系是重量级的实现这一特点。

## 容器化

有了虚拟化技术，看上去好像对于物理机的资源分配问题已经得到了很好的解决，但是实际上并没有。因为虚拟化技术存在性能损耗和资源开销大等诸多的问题，所以人们将目标逐渐的瞄准在容器技术上。2013年Docker的开源，随后在业界迅速蹿红，各大厂商也纷纷从虚拟化技术转向容器技术，然后随着2014年Google开源K8S(Kubernetes)，Kubernetes + Docker的模式逐渐成为了云原生技术栈的实际标准。

### 虚拟化VS容器化

为什么虚拟化技术会在云原生中逐渐掉队（也不能说掉队，两者核心解决的问题不太一样，隔离级别也不一样，但是容器化更加轻量），我们可以通过下面这张图来看一下：

![虚拟化VS容器化](<../images/redirect_75.png>)

虚拟机(virtual machine)共享同一个服务器的物理资源的操作系统，它是通过虚拟层hypervisor来和宿主机进行交互的，在实际的使用中虚拟机技术会存在以下问题：

**资源开销大** ： 每个虚拟机都有自己的操作系统，这将消耗更多的 CPU 和内存资源。
**启动时间长** ： 由于每个 VM 需要启动操作系统，启动时间通常较长，影响灵活性。
**复杂性高** ： 管理多个虚拟机可能涉及更多的复杂性，尤其是在网络和存储管理方面。
**资源损耗大** ： 最后一点也是最关键的一点，因为虚拟层的存在，导致虚拟机技术会存在一定的资源损耗的问题。

相比之下容器技术就轻量很多，它没有复杂的中间层，是利用宿主机原生的资源隔离能力来实现的，所以它足够轻量，具有占用资源少、启动速度快等特点。

两者本质上存在较大的差异，总结起来可以从下几个方面说明：

**操作系统的实现** ：

虚拟机：虚拟机拥有独立的OS内核，可以把它看成一个独立的机器，它通过虚拟层和宿主机进行交互。
容器：容器没有独立的OS内核，它是运行在宿主机中的一个"独立空间"。

**性能** ：

虚拟机：虚拟机的运行依赖虚拟层hypervisor，这里面会有较大的性能损耗。
容器：容器运行于宿主机的OS中，它的本质是一组特定的进程集，没有额外的性能损耗。

**虚拟化层次** ：

虚拟机：通过虚拟层hypervisor对宿主机的CPU、内存和磁盘等进行虚拟化，属于硬件层次。
容器：原生运行在宿主机OS中，通过OS的资源隔离策略来进行隔离，属于软件层次。

**启动速度** ：

虚拟机：启动过程需要加载整个虚拟机的OS，整个启动过程比较慢。
容器：本质上是宿主机OS的进程集合，整个启动过程非常快。

可以看出来，容器技术相比较于虚拟机的实现要轻量很多，这也就是为什么容器技术可以“如日中天”。我们内部目前无论有状态的中间件、还是无状态的应用基本都已经实现了容器化。我们内部熟悉的ASI、ACK和ASK都是容器化的解决方案，我们熟悉的Serverless的Fass和Bass本质上也是建立在以K8S为核心的基础设施调度平台上的。

PS：说到容器化我们经常和Docker联系到一起，但是两者并不是一个概念，Docker只是容器化技术实现的一个现象级产品。

## Docker

Docker是容器技术的佼佼者，最初的发起者是DotCloud公司，并在2013年开源。在那个openstack、cloud foundry等pass解决方案神仙打架的时代，Docker看上去是那么的格格不入。DotCloud也和Red Hat、Pivotal等著名公司也不在一个量级，但是也就是Docker直接掀翻了Pass平台的桌子。

随着Docker的开源，Docker技术也瞬间风靡全球，备受各家的追捧。Docker主要解决了资源隔离、快速部署与启动、版本控制、可移植性、持续集成与持续交付和资源利用率等核心问题，而且因为Docker的轻量级实现使得微服务架构的开发和部署也变得非常简单。

### 一句话简单描述

Docker可以帮助开发者打包、分发和运行应用程序，Docker 就像一个“容器”，可以把你的应用程序和它所需的所有组件（比如库和环境设置）打包放在一起，无论你在什么机器上运行这个容器，应用程序都能正常工作，整个容器看上去就像一个单独的机器一样，而且保证整个过程是足够轻量的。

### Docker的组成

![](<../images/redirect_76.png>)

**Docker Engine：**

- Docker Daemon（dockerd）：后台服务，处理 Docker 命令，并管理容器的生命周期。
- Docker CLI（命令行接口）：与 Docker Daemon 进行交互的命令行工具，用于进行容器的构建、运行等操作。

**Docker Registry：**

- 私有镜像仓库，用于存储和分发 Docker 镜像。用户可以搭建自己的 Docker Registry，便于管理内部镜像。

**Docker Image：**

- 仅读的程序部署模板，用于创建 Docker 容器。镜像是容器的基础，包括应用程序及其所有依赖项，用户可以从 Docker Hub 等镜像中心下载预定义的镜像或者自己构建镜像。

**Docker Container：**

- 运行中的镜像实例，容器是轻量级的、可移植的和自给自足的环境。容器包含了应用程序及其所有必要的依赖，确保在不同环境中一致地运行。

**Docker Volume：**

- 用于持久化数据的 Docker 存储机制，允许用户在容器之间共享数据，并在容器重启或删除后保留数据。

**Docker Network：**

- 用于容器间的网络通信配置。Docker 管理自己的网络，允许容器通过多个网络接口相互连接。

**整个部署过程可以简单描述为：**

1. Docker CLI 调用API请求Docker Daemon。
2. Docker Daemon从Docker Registry拉取Docker Image到Server。
3. Docker Daemon对Docker Image进行解压缩调用Linux的API来创建Docker Container，同时分配Docker Volume和Docker Network。
4. Docker Daemon调用启动脚本中指定的command，启动目标进程。

这样基本就完成了一个Docker实例的部署，可以看到对于一个镜像的部署而言，是非常简单快捷的。

### Docker容器镜像

容器镜像是Docker如此成功的一个非常重要的因素。镜像本质上是我们对我们的应用以及应用的运行环境的打包，通俗讲就是打包一个完整的操作系统文件 + 你的自定义的应用程序文件。这些文件信息在容器的运行时部署之后，会进行解压，同时通过chroot来修改我们容器运行时的工作目录信息。使得我们登录到对应的容器时，看到的视图就是我们镜像解压之后的文件列表。

**而容器镜像就是一种独特的基于分层管理的打包方式，这种打包方式是Docker首创的，也是它能够异军突起的重要原因。**

通常我们的应用在部署之前需要制作容器的镜像，比如在我们应用中的一系列Dockerfile，如下图所示：

# 用基础镜像地址替换下方镜像地址
FROM reg.docker.alibaba-xxxx.com/aone-base/xxxxx.xxxx

ARG appname=xxxxxx

RUN echo "APP_BASE_DIR_NAME=${appname}" >> /home/admin/setappenv.sh

VOLUME /home/admin/${appname}/logs /home/admin/${appname}/forest

# 将应用启动脚本和配置文件复制到镜像中
COPY environment/common/bin/ /home/admin/${APP_NAME}/bin
.....

这些配置里有一系列的"Docker原语"，这里有一些关键的原语做一下解释:

1. **FROM:** 表示拉取指定的基础镜像，之所以有基础镜像是为了解决镜像不可控的问题。所以构建了一系列的基础镜像，我们的应用镜像会在基础镜像之上进行"堆叠"。
2. **RUN:** 运行shell命令，这会在容器运行时执行对应的命令。
3. **VOLUME：** 将容器的指定目录挂载到宿主机的指定目录下，这主要是为了持久化数据。因为Docker采用堆叠的方式进行持久化，如果不挂载到宿主机的指定目录下，那么在容器重启之后，日志会丢失。
4. **COPY：** 将应用代码中相关位置的文件复制到镜像的指定目录位置上，这里主要是对nginx的文件进行了复制。因为容器中不只要运行应用进程，还会运行nginx，所以需要把nginx的配置文件copy进来，而nginx的运行文件已经打在了基础镜像中了。
5. **ENTRYPOINT：** 应用执行的入口，在应用启动的时候会通过这些脚本来启动对应的进程，可以看到这里是start.sh启动脚本。

所有这些原语都会在基础镜像上进行 **“堆叠”** ，这种堆叠操作会形成一个一个的 “层”，每一个原语对应一个层，直到所有的原语执行完成，可以看一下基础镜像体会一下：

# 基于基础镜像
FROM reg.docker.alibaba-xxxx.com/appdocker/aliosxxxcc65-min

# 指定应用名字，配置在$APP_NAME.release文件里
# 从 build.tools.docker.args=--build-arg APP_NAME=${APP_NAME} 传入
ARG APP_NAME
ENV APP_NAME=${APP_NAME}

ARG SAR_VERSION=20xx-xx-release.clone.cloudpath
......

# 启动容器时进入的工作目录
WORKDIR /home/admin/$APP_NAME/logs

#容器启动时自动执行的脚本，我们一般会将应用启动脚本放在这里，相当于系统自启应用
ENTRYPOINT ["/home/admin/start.sh"]

对于层的描述，可以以我本地的Redis镜像为例简单看一下。每一个原语都会引起镜像文件的变更，这样的变更在镜像中会反映成一个镜像层：

![](<../images/redirect_77.png>)

但是这种"堆叠"方式也存在一个问题，那就是容易产生各个版本的镜像文件，导致存储浪费和混乱。所以我们需要将不同阶段的镜像抽象成一个个基础镜像，并在基础镜像上进行堆叠。就像类的继承一样，将共同的内容沉淀在父类中，这里就是沉淀在基础镜像中。所以你可以看一下你自己的应用镜像也是从另外一个基础镜像上进行 **“堆叠”** 而来的。

## 理解容器实现的本质

可能你觉得Docker这么强大，那它的实现一定十分的复杂，但是实际上Docker的实现完全是基于OS提供的基础虚拟化的能力的，它的实现原理可以说非常简单。具体来说是三种能力，在Linux中这三种能力就是namespace、cgroup和chroot。

谈到namespace和cgroup比较有意思的是这两尊虚拟化的“大神”长期游走于人们的视野之外，直到Docker的出现将他们"发扬光大"，所以了解了namespace、cgroup基本上也就弄懂了容器。当然除了namespace和cgroup之外还有chroot，它的核心能力就是改变容器内进程可识别的根目录，所以你登录容器之后看到的根目录本质上是宿主机下的一个普通子目录。

**总结一下：容器 = namespace + cgroup + chroot**

## 容器是怎样实现隔离的

## namespace

Linux namespace 是Linux内核的一项重要特性，主要用于实现进程间的隔离与资源的虚拟化。namespace 的本质实际上是划分了一部分操作系统资源（CPU、内存和网络等）的集合，然后将一个进程及其子进程运行在这样的资源集合之上，继而形成了一个个隔离的运行环境。这样一个个隔离的环境在进程视角看来就像一个个独立的机器一样。

对于namespace的发展历史，可以简单概括如下：

**2000年:** 最早的 namespace 概念是在 Linux 2.4 版本中引入的，用于实现一些基本的隔离功能，主要是通过使用 chroot 等系统调用。
**2006年:** Linux 内核 2.6.0 引入了新的 namespace 概念，尤其是进程的 PID namespace，允许进程创建一个虚拟的进程 ID 空间，增强了进程隔离。
**2008年:** 随着更多 Namespace 类型的引入（如网络namespace、用户namespace、挂载namespace等），Linux 的隔离机制得到了显著增强，为后来的容器技术（如 LXC 和 Docker）奠定了基础。
**2013年:** Docker 的发布使得 namespace 真的进入了大众视野，成为容器技术的重要组成部分。Docker 利用 namespace 实现了轻量级的隔离和资源管理。

Namespace的类型主要有下面几种，它们其实涉及到OS资源的方方面面：

- PID namespace：进程ID隔离。
- Network namespace：网络栈隔离，包括网络接口、地址、路由等。
- Mount namespace：文件系统挂载点隔离。
- UTS namespace：主机名和域名隔离。
- IPC namespace：进程间通信隔离。
- User namespace：用户和组 ID 隔离。
- Croup namespace：控制组隔离。
- Time namespace：系统时钟隔离。

在上述namespace之中，通常我们关注的最多的是PID namespace、Network namespace和Mount namespace。这分别对应着进程隔离、网络隔离和存储隔离，它们是这些Namespace核心中的核心，接下来我们逐一做一下说明。

## PID namespace

### 什么是PID namespace

不知道你是否疑惑过，当我们使用一个容器时，我们的容器中运行着我们的应用程序。当我们使用ps命令查看所有的进程时(如下图)，容器是如何保证我们只能看到当前容器内的进程的，而对于同物理机下的其他容器内的进程对我们不可见的。 这里面主要用到的就是PID namespace。

![](<../images/redirect_79.png>)

对于PID namespace，最朴素的理解你可以理解为将进程归属于不同的范围，这个范围就是namespace，不同的namespace之间的进程是彼此不可见的。 不过namespace之间存在上下级关系，父namespace是可以观测到子namespace的进程的，这也就是为什么从你的物理机上可以观测到容器内的进程的原因。PID namespace的隔离逻辑大致可以用下图进行描述：

![](<../images/redirect_80.png>)

### PID namespace的实现

关于PID namespace的实现，本质上是namespace和一组进程的关系。我们可以从源码层面大致来梳理一下namespace和进程的关系。这种进程和namespace的关联关系在内核上是维护在task_struct的nsproxy之上的，task_struct其实就是OS内对一个进程的描述：

```java
struct task_struct {
    ......
    /* Filesystem information: */
    struct fs_struct        *fs;

    /* Open file information: */
    struct files_struct        *files;

    /* Namespaces: */
    struct nsproxy            *nsproxy;
    ......
};
```

可以看到nsproxy中有很多的namespace类型，我们重点关注的是pid_namespace：

```java
struct nsproxy {
    atomic_t count;
    struct uts_namespace *uts_ns;
    struct ipc_namespace *ipc_ns;
    struct mnt_namespace *mnt_ns;
    struct pid_namespace *pid_ns_for_children;
    struct net          *net_ns;
    struct cgroup_namespace *cgroup_ns;
};
```

对于每一个进程都有它关联的pid_namespace。和进程树类似，namespace也具备传播特性，也就是子进程默认继承父进程的namespace。

在Linux启动时会为1号进程，也就是init进程创建一个初始的nsproxy，也就是init_nsproxy。它是1号进程的初始化nsproxy结构，init_nsproxy中的init_pid_ns是初始化的pid namespace:

```java
struct pid_namespace init_pid_ns = {
    .kref = KREF_INIT(2),
    .idr = IDR_INIT(init_pid_ns.idr),
    .pid_allocated = PIDNS_ADDING,
    .level = 0,
    .child_reaper = &init_task,
    .user_ns = &init_user_ns,
    .ns.inum = PROC_PID_INIT_INO,
```
#ifdef CONFIG_PID_NS
    .ns.ops = &pidns_operations,
#endif
};

这里的idr则是关联的此PID namespace下的所有进程ID，这是一个RADIX_TREE的结构：

#define IDR_INIT_BASE(name, base) {                    \
```java
    .idr_rt = RADIX_TREE_INIT(name, IDR_RT_MARKER),            \
    .idr_base = (base),                        \
    .idr_next = 0,                            \
}
```

PID namespace 就是以这种方式组成了一个树形结构，而不同的进程分别挂在不同的namespace之中。由于在使用ps等命令查看进程时只能看到当前namespace的进程，所以归属于不同的namespace之间的进程又是互相不可见的。另外每一个进程创建的子进程会继承父进程所属的namespace，这样你就可以把进程基于namespace划分成多个逻辑上的“进程组”，这样也就实现了隔离。

你可以试想一下，当你在容器中执行PS命令时，本质上也是通过shell创建了一个PS进程，而这个PS进程是基于容器内的进程创建而来的，自然而然它只能看到容器内的进程列表，是不是很神奇。

## Network Namespace

Network namespace 在原理上实现和PID namespace相似，主要用于网络资源的隔离。因为Network namespace涉及到网络资源的隔离，而网络协议栈整体又非常复杂，而且还涉及到单个物理机上多个容器之间的通信，多个物理机间的容器网络互通等等场景，使得Network namespace的实现也要复杂得多。

不过首先要着重明确的是不同Network namespace下的容器都有一份属于自己独立的网络空间，这个网络空间包括 **端口号区间、协议栈、驱动设备、网卡设备等** 。这么一听可能会比较疑惑，尤其是网卡设备和驱动设备，同一个物理机上应该只有一个才对（当然也有多网卡方案，这里只是举例），为什么同一个物理机上的不同容器可以拥有各自独立的驱动设备和网卡设备？

其实这些所谓的设备本身其实都是内核为了实现容器化隔离而虚拟出来的，它们可以像真实设备一样进行通信，但是却没有对应的物理设备。所以这样你就可以理解为什么在你的容器中可以使用80端口，而同一个物理机下的其他容器也可以使用80端口，而不会冲突。因为它们属于不同的Network namespace、不同的协议栈。

**一定要注意：一个Network Namespace拥有独立的端口号区间、协议栈、驱动设备和网卡设备等网络资源。**

### 跨物理机间容器通信

本机通信其实相对来讲比较容易，因为docker0的存在，无论是本机容器之间的通信，还是容器和物理机的通信都是可以实现的。但是如果你尝试在不同的物理机上的容器进行通信，那么这会是比较困难的，但是也不是不可能，我们需要实现以下几步:

1. veth到docker0网桥的通信。
2. docker0网桥到物理网卡的通信。
3. 当前物理机到其他物理机的通信。
4. 其他物理机到当前物理机的通信。
5. 当前物理机到目标容器的通信。

以上这些步骤的转发和请求一部分依赖于网络协议栈基础通信能力，一部分依赖于内核的转发和IP替换机制，这里我们还是重点先了解一下内核的转发和IP替换机制。

内核的转发和IP替换机制核心的实现是基于netfilter和iptables的，它们是整个容器网络虚拟化的基石，无论是Docker还是K8S都是通过使用Netfilter和Iptables来实现跨主机的容器通信的。

#### Netfilter

Netfilter是在Linux2.4版本中引入的子系统，最初的设计是为了实现内核防火墙。它定义了一整套的通用统一的hook函数机制，使得数据包的过滤、处理、地址转换、访问控制和带宽限制等成为了可能。

通俗讲Netfilter的本质是在网络数据包处理流程中预留一些钩子，用户可以基于这些钩子自定义处理逻辑，以实现上述提到的功能。在虚拟化网络中，我们通常可以基于Netfilter定义一些转发和伪装规则来实现容器内网络协议栈的请求和转发。

![](<../images/redirect_84.png>)

上图中定义了Netfilter的五个钩子：

**INPUT：** 在数据包经过路由并到达本地系统后触发。它主要用于处理本地接收的数据包，比如对于本地应用程序的保护；
**OUTPUT：** 在本地生成的数据包被传出之前触发。它可以用于对本地应用程序生成的出站流量进行监控和过滤。
**FORWARD：** 在经过本地计算机的转发状态的数据包上触发，主要用于过滤经过本地机器但是不发往本地机器的流量，例如在路由器或网关上进行过滤；
**PREROUTING：** 这个钩子在数据包到达路由之前被触发，用于对进入本地系统的网络数据包进行处理，如NAT（网络地址转换）和防火墙规则。
**POSTROUTING：** 在数据包离开路由之后触发。它主要用于进行最后的处理，如DNAT操作，将数据包转换为最终的发送格式。

可以看到上面叙述的这些钩子其实就是在网络流量发送和接收过程中涉及的钩子入口。如果想要在这些钩子上配置处理逻辑，我们还需要另外一个组件，那就是Iptables。

#### Iptables

Iptables是用户空间的一个程序，通过netlink和内核的netfilter框架打交道，负责往钩子上配置回调函数。

iptables核心思想可以概括为五条链 + 五张表：

**五条链：**

即对应着上面的INPUT、OUTPUT、FORWARD、PREROUTING和POSTROUTING。

**五张表：**

**filter 表：** 这是默认的表，主要用于网络数据包的过滤。它包含了最常见的链（如 INPUT、OUTPUT 和 FORWARD），用于决定是否允许或者拒绝通过的网络流量。

**nat 表：** 该表用于进行网络地址转换（NAT）。它主要用于修改数据包的源地址或目标地址。这在进行端口转发或者对内部网络的 IP 地址进行映射时非常有用。常见的链包括 PREROUTING、POSTROUTING 和 OUTPUT。

**mangle 表：** mangle 表用于修改数据包的某些特性，比如修改 TOS（服务类型）或 TTL（生存时间）等。它在网络流量管理和 QoS（服务质量）方面常常使用。常见的链与 filter 表相同。

**raw 表：** raw 表用于配置数据包的跳过连接跟踪或修改记录。它可以提高性能，允许某些流量不经过连接追踪机制。

**security 表：** security 表用于实现强制访问控制（MAC），提供额外的安全性。它是 SELinux 等安全模块用于检查和实施策略的地方。

通俗一点讲就是每一个Netfilter的钩子切点中都可以使用上述5张表来定义一些规则，网络流量依次使用这些规则处理相应的逻辑。但是实际上每个钩子是无法利用所有的表的，它们有一个固定的对应关系：

##### 物理机网卡到对端物理机网卡

这里的实现涉及到一点非常重要的规则就是 NAT。试想一下如果物理机网卡仅仅是做 ip 数据包的转发，那么这些数据包的源 ip 地址应该是172.17.0.3，因为这是容器发出来的数据包。这样的数据包经由宿主机转发到对端的物理机是可以走通的，但是对于对端物理机对数据包的响应却是无法实现的。因为对端物理机认为源 ip 为172.17.0.3（基于报文），但是基于此 ip 是找不到对应的机器的，因为容器IP地址并没有出现在物理网络中，就比如下面的场景：

注：192.168.124.17为目标物理机ip

### 如何更优雅的实现跨主机的网络通信

上面我们看到，使用Linux本身提供的Netfilter + Iptables的方式是可以实现跨主机容器间的网络通信的。但是这样的方式其实是基于复杂的规则实现的，那么有没有一种比较轻量级的解决方案来屏蔽这些复杂的规则来让这样的通信更加简单呢？有的，就是基于“隧道”技术实现的虚拟网络技术，这类虚拟网络技术的代表有像VXLAN、Macvlan和IPvlan等等。

#### 从网络隧道说起

网络隧道技术是指在两个网络节点之间建立的一条虚拟连接，它可以包裹各种类型的网络协议，使得数据包在互联网上进行传输时都是隐蔽的，我们最常见使用的隧道技术就是VPN。

隧道技术的基础是tun/tap技术，简单讲tun/tap本质上是一种网络设备，你可以理解为它们是一种虚拟网卡。但是这个网卡比较特殊，所有通过此网卡接收和发送的数据包都要经过运行在用户空间的一个“钩子”，如下图所示：

![](<../images/redirect_89.png>)

APP1发出的数据包经过网络协议栈的时候，会被路由到tun0。tun0会将这些数据包上行交给另外一个运行在用户空间的APP2，在APP2中可以对这些数据包进行加密、脱敏或替换等。然后APP2会将对应的数据包再重新投回网络协议栈，最后使用eth0网卡将数据包发送出去。

而在接收端也一样，网卡接收到对应的数据包之后会将这些数据包交给tun设备。tun设备会对这些数据包进行解密等处理操作，然后重投回网络协议栈，最终被目标应用程序接收到。如果忽略底层的网络传输过程，从两端的应用程序的视角来看，好像是建立了一个"隧道"使两个应用程序可以进行通信，可以根据下图来体会一下：

![](<../images/redirect_90.png>)

基于这种隧道技术的思想，虚拟化的网络技术逐渐发展起来。这种虚拟化的网络方案核心的思想是在物理的通信网络层之上基于隧道技术构建起了一套虚拟的网络通信层，传统的容器间的通信就是运行在这种虚拟的网络层面的。这样就可以使得容器间的通信基于容器的IP来实现，而不需要配置繁复的规则，示意图如下：

![](<../images/redirect_91.png>)

接下来我们会以VXLAN为例，描述一下这种虚拟网络的实现。

PS: 关于隧道的实现，本质上就是将内核的数据包再转发到用户空间一次，基于用户空间的一些规则对数据包进行加工（加密、解密、替换数据包等等操作），以达到和目标机器建立稳定、可靠的通信链路，这种链路看起来就像一个隧道一样。

#### VXLAN

VXLAN是2011年伴随虚拟化技术而兴起的一种虚拟化网络通信的解决方案，主要用于解决VLAN面临的扩展性不足的问题(支持的子网数量有限制)。VXLAN的技术标准RFC 7348于2014年发布，正式定义了VXLAN的技术细节。随后VXLAN技术高速发展，很多知名企业都使用VXLAN来解决虚拟网络问题，比如Cisco、Juniper和Arista等。

VXLAN是Linux内核本身就支持的一种网络虚拟化技术。所以VXLAN可以完全在内核态实现上述封装和解封装的工作，从而通过与前面相似的“隧道” 机制构建出覆盖网络。

VXLAN的覆盖网络的设计思想是，在现有的三层网络之上“覆盖” 一层虚拟的、由内核VXLAN模块负责维护的二层网络，使得这个VXLAN二层网络上的“ 主机” (虚拟机或者容器都可以)之间，可以像在同一个局域网里那样自由通信。

这些“ 主机” 可能分布在 不同的宿主机上，甚至是分布在不同的物理机房里。 为了能够在二层网络上打通“隧道”，VXLAN会在宿主机上设置一个特殊的网络设备作为 “隧道” 的两端。这个设备叫作VTEP (VXLANtunnel endpoint，虚拟隧道端点)，整个通信示意图如下所示：

## 总结一下

在一台Linux宿主机中，内核通过使用各种类型的namespace将各种进程、存储、网络等资源进行了逻辑上的空间划分。使得这些被划分出来的区域都有自己的运行空间，看上去就像一个个相对独立的Linux系统一样。我们可以在这些“子系统”中自由的运行我们的进程，使用独立的存储资源而不相互干扰，这就是各种namespace的作用。

## 容器是怎样实现资源限制的

谈到虚拟化，对于资源使用的限制是一个没办法绕过的话题。在单个物理机上我们可以虚拟化出多个容器，但是如何为这些容器分配计算资源，是一个非常核心且困难的问题。好在Linux内核对于容器化资源分配和隔离有相当好的实现，这也就帮助我们解决了这个问题。

在Linux中对于容器化这种软资源隔离和分配主要使用cgroup来实现，cgroup（Control Group）是Linux内核中的一个特性，用于将进程分组并对这些组施加资源限制和监控。这意味着系统管理员可以控制每个进程组可以使用的CPU时间、内存、网络带宽等资源。

## cgroup是什么

cgroup的概念最早由Google的工程师提出，旨在更好地管理Linux服务器上的资源。最初这一功能主要是为了满足大型集群和数据中心对资源管理的需求，后来由于Docker的崛起逐步进入大家的视野。直到今天cgroup都是云原生基础底座资源隔离和分配的主流方案。

**cgroup通俗一点讲就是通过配置创建一个个资源组，然后将进程和这些资源组进行关联，Linux内核在进程调度和运行时会基于这些配置来对进程进行资源限制。**

在Linux 2.6.24版本中，cgroup被正式合并到Linux内核中，随着cgroup的使用增加，内核开发人员不断增强其功能。这一时期增加了许多特性，如新增的控制器（例如memory、cpu、cpuset等），使得cgroup能够支持更多的资源类型和管理需求。
cgroup最初的版本被称为cgroup v1，但是它存在一定的设计局限性。为了解决cgroup v1的一些设计缺陷和局限性，cgroup v2在Linux 4.5版本中开始引入，cgroup v2采用了更为统一和一致的接口结构，简化了控制器（如对资源分配的管理）、以及进程的层次结构，cgroup v2也是目前最新的Linux内核默认的cgroup版本。

接下来我们会以CPU资源隔离为例对cgroup做一个简单的介绍。

## cgroup是怎样实现资源限制的（以CPU为例）

### 从CFS开始说起

#### CFS的基本思想

CFS（Completely Fair Scheduler）是当前Linux主流使用的用户进程的调度器，在2.6.23之后成为默认的用户进程的调度器，它的核心思想是强调让每一个进程尽量公平的分配到CPU时间。

CFS在实现上的核心思想是将进程组织在N棵红黑树上（数量取决于逻辑核个数），然后通过进程运行的时间(vrutime)来为进程进行从小到大排序，然后按照排序来对进程进行调度，可以按照下列的流程来大致理解一下：

![](<../images/redirect_98.png>)

在CFS中每个CPU的逻辑核心都有这样一个进程调度队列：

![](<../images/redirect_99.png>)

进程和调度队列的关系可以使用Linux内核内的进程关系描述：

![](<../images/redirect_100.png>)

task_struct是进程在Linux内核中的描述，内核中task_struct关联了sched_entity中的rb_node，这样就把进程和CFS队列红黑树进行了关联。

在进程调度过程中是否要调度一个进程主要取决于这个进程在红黑树中的位置，越靠左的节点会越先被调度到，而这个排序的过程主要是使用一个被称为vruntime的属性。

**vruntime表达的是进程在该CPU上已经运行的时间**

在每次进程从cpu调度走时（发生进程切换），会更新被调度走的进程的vruntime字段，标识此进程运行了“多久”。

具体的计算规则如下：

vruntime = 实际运行时间 * (NICE_0_LOAD / curr->load.weight)

核心想要表达的就是:

**当前实际执行的时间 * 权重因子等于vruntime，权重因子主要是基于nice值来设定，nice值越小那么算出来的vruntime越小，那么进程在红黑树中越靠左，就越快被调度到，实际占用的时间也越长。**

这里其实比较好理解，因为CFS是完全公平调度，那么也就意味着得到越少时间片的进程就越要尽快调度它，更多的让它拥有CPU时间片。

#### 触发调度的时机

对于进程调度的触发时机主要分两种，一种是主动让出，另外一种就是运行时间过长被动让出。

##### 主动让出

主动让出主要有以下几种场景:

1. 调用线程的sleep()、yield()等，这会主动调用CPU进程调度程序，使当前的CPU放弃时间片，同时内核会维护一个定时器，当达到指定时间时会触发唤醒等待进程。
2. 等待IO操作的场景，比如磁盘、网卡的读写，此时进程会加入到对应文件描述符的等待队列中，等待对应设备的IO中断完成数据的拷贝，然后重新唤醒等待队列中的进程，最后再次调度到CPU执行队列中。
3. 信号量的等待，也就是我们常见的锁。等待锁的进程会自动加入到锁等待队列中，等待前序持有锁的线程唤醒等待队列中的线程，最后将被唤醒的进程加入到CPU的调度队列之中。

最直观的例子就是，Socket通信中的等待协议栈的数据返回的流程：

![](<../images/redirect_101.png>)

##### 被动让出

被动调度主要是指Linux会周期性地触发进程集的重新调度，主要基于timer interrupt来实现。timer interrupt会周期性地运行，并且会定时将每个进程执行过的时间都换算成vruntime。然后判断是否当前进程已经执行了足够长的时间，如果是，那么挂起当前进程，同时选择一个vruntime较小的进程执行，在CFS中就是进程红黑树中最左边的节点。

在被动让出的场景，主要分两种：

1. 当前进程的实际运行时间比根据调度周期算出来的预期时间长了，那么需要让出CPU，这种场景的核心就是控制一个进程可以占用CPU的时间。如果当前系统内进程比较少，那么这个预期时间差就会比较大，反之则会比较小。这也很好理解，压力大的时候，大家都要分一点时间片，避免饥饿的问题。
2. 当前进程的vruntime已经比红黑树中最左侧的节点的任务的vruntime已经大了很大一部分，这个时候需要对当前进程进行抢占。

### 容器进程的调度

从上面关于 cgroup 的关联关系，我们可以看出来 cgroup 本质上是对一系列进程的集合进行资源的管控，这些资源包括 CPU、内存、IO 等等。在内核中进程的基础结构 task_struct 在实现上是和这些 cgroup 进行关联的。进程内维护着一个 cgroup_subsys_state，它关联着和本进程相关的各种 cgroup 规则，比如，task_group、cpuset 等等，在内核实际对进程进行资源限制时使用的都是这些具体的规则。

聚焦到 CPU 上，我们关注的规则主要就是 task_group：

    #endif

};

在cfs_bandwidth 中有几个比较重要的属性，比如runtime、quota 和period：

struct cfs_bandwidth {
    #ifdef CONFIG_CFS_BANDWIDTH
```java
    raw_spinlock_t        lock;
    ktime_t            period;
    u64            quota;
    u64            runtime;
    s64            hierarchical_quota;

    u8            idle;
    u8            period_active;
    u8            slack_started;
    struct hrtimer        period_timer;
    struct hrtimer        slack_timer;
    struct list_head    throttled_cfs_rq;

    /* Statistics: */
    int            nr_periods;
    int            nr_throttled;
    u64            throttled_time;
```
    #endif
};

1. runtime 代表了当前 cgroup 内所有进程可用的时间片长度。
2. quota 代表了 cgroup 配置中配置的单位时间内可以使用的长度。
3. period 代表了 cgroup 配置中配置的单位时间内分配的时间片长度。

由于每一个 task_group 都有和逻辑核数相同数量的进程队列（cfs_rq），每一个队列在 CFS 调度的时候都需要消耗时间片，每一个进程队列的时间片用runtime_remaining 表示，代码如下：

```java
/* CFS-related fields in a runqueue */
struct cfs_rq {
    struct load_weight    load;
    unsigned int        nr_running;
    unsigned int        h_nr_running;      /* SCHED_{NORMAL,BATCH,IDLE} */
    unsigned int        idle_h_nr_running; /* SCHED_IDLE */

    u64            exec_clock;
    u64            min_vruntime;
    struct rb_root_cached    tasks_timeline;
    struct sched_entity    *curr;
    struct sched_entity    *next;
    struct sched_entity    *last;
    struct sched_entity    *skip;
```
#ifdef CONFIG_CFS_BANDWIDTH
```c
    int            runtime_enabled;
    s64            runtime_remaining;

    u64            throttled_clock;
    u64            throttled_clock_task;
    u64            throttled_clock_task_time;
    int            throttled;
    int            throttle_count;
    struct list_head    throttled_list;
#endif /* CONFIG_CFS_BANDWIDTH */
#endif /* CONFIG_FAIR_GROUP_SCHED */
};
```

task_group中的每一个队列都需要从cfs_bandwidth分配时间，并保存在runtime_remaining中。每次进程运行结束时都需要从runtime_remaining 扣除运行时间，如果时间不够了那么就要从cfs_bandwidth 的runtime 进行申请。如果runtime 也没有剩余的时间片了，那么当前的 task_group 会被移出 CFS 调度队列，因为已经没有时间片使用了。

所以这里比较关键的就是runtime什么时候被初始化、什么时候会增加。这直接决定了一个 task_group 拥有的时间片大小，而runtime 时间的更新主要是依靠 period_timer 和 slack_timer两个定时器。

period_timer 会依照cgroup设定的周期period来周期性地为task_group补充runtime，补充的大小为cgroup定义的quota。这里需要注意的是经过补充之后的runtime 是无法超过quota 的，也就是说在一个周期内task_group可以使用的时间上限为quota。

而slack_timer的作用主要是将一些运行时间比较短即发生阻塞的进程所分配的runtime_remaining返还给task_group 的runtime，以便于其他的进程可以使用这些时间片。

所以对于cgroup中cpu资源使用的限制，核心是限制cgroup下的进程在 cpu.cfs_period_us 这样一个周期内可以最多使用长度大小为 cpu.cfs_quota_us 的时间片，而不是分配了几个核心。

**所以当你设置cpu.cfs_period_us 200000、cpu.cfs_quota_us 100000的时候，本质上是在单位100ms的时间周期内，为这个容器填充200ms的CPU可使用时间，所以这就相当于2个核心了。**

当然这里会出现一种情况，就是在单位时间窗口开始的时候，系统的CPU使用率非常高，把本窗口的CPU时间全部耗尽了。导致你的进程一直拿不到CPU的使用权，你的接口RT就会飙升。这种现象就是throttle，当你发现你的throttle次数变多的时候，你可能就需要调整你的cgroup了。

### CPU权重分配

通过上面的描述，我们明白了 cgroup 对于一个组内的进程的 cpu 使用的上限约束，理论上来讲一旦设定了上限之后，在 cgroup 内的进程是没有办法超出这个上限的，但是这又带来了一个问题，就是资源浪费问题。

假设我有一个 48c 的物理机，我全部用来分配容器，每个容器 4c，那么这就意味着我可以分配 12 个容器。但是因为业务属性的不同，这些容器的水位也差异很大，往往不能更好的充分利用。（比如 OLTP 的在线业务和离线计算任务的差异性。OLTP相关的业务往往CPU使用要求比较低、但是离线计算的CPU使用要求很高，所以你需要一个合理的调配能力在保证稳定性的前提下实现资源利用率的最大化。）

所以这个时候我可能更倾向于在 48c 的物理机上分配 16 个 4c 的容器，虽然超出了物理机的上限，但是我可以更充分地利用 cpu 的资源。然后我在底层用一套权重机制将 CPU 的资源基于不同的权重来将 CPU 资源分配到承载不同业务的容器上，以达到最大化资源利用率的目的。甚至是将在线应用和离线任务部署在一起，以达到最大资源利用率的目的，这也是我们日常使用最多的离线混部的模式。

要实现这样的模式，需要前面提到的一个配置 cpu.share，cpu.share 定义了一套 cpu 资源的权重体系，来支持我们为不同的 cgroup 分配资源的权重占比。CFS 在进行进程调度时会基于此权重来计算待调度进程或task_group 的 vruntime，具体计算公式如下：

vruntime = real_runtime / weight

因为vruntime 是决定一个进程被调度的时间的核心因素。当权重设置越大时vruntime 越小，那么被调度的时间越长，vruntime 越大，那么被调度的时间越短。这样就实现了 cpu 资源按照权重分配的目的。举个例子，一台机器 16c 的物理机上有 2 台权重为 1024 的容器，2 台权重为 2048 的容器和 1 台权重为 4096 的容器，那么：

1. 权重为 1024 的容器在调度时使用的核心数为 (1024 / 10240) * 16 = 1.6c
2. 权重为 2048 的容器在调度时使用的核心数为 (2048 / 10240) * 16 = 3.2c
3. 权重为 4096 的容器在调度时使用的核心数为 (4096 / 10240) * 16 = 6.4c

这里值得注意的是：

cpu.share 只是基于权重来实现进程资源的调度，如果某个容器的 CPU 使用率增长比较高，它会抢占其他的容器的 CPU 资源，导致其他 CPU 的使用率升高(因为st升高了)，这个时候就需要 cgroup 的资源限制能力了。

### 实际生产中的权重分配

对于我们实际生产中，对于cpu的核数是怎样分配的呢，这一点我们可以通过pod部署的yaml文件和pod上的配置得出结论:

resources:
  limits:
    cpu: '4'
    memory: '8589934592'
  requests:
    cpu: '3'
    memory: '8589934592'

在诺曼底中描述的yaml文件显示，我的pod的request的大小为3核，而limit为4核，也就是意味着我的pod的权重设定计算结果应该为3核，而使用上限应该是4核。

我们再从pod上看一下配置：

$cat /sys/fs/cgroup/cpuset,cpu,cpuacct/cpu.shares
3072

可以看到cpu.shares为3072，这也就意味着，我的pod按照权重可以分到3核CPU。

再看一下对应的cpu.cfs_period_us和cpu.cfs_quota_us设置：

$cat /sys/fs/cgroup/cpuset,cpu,cpuacct/cpu.cfs_period_us
100000
$cat /sys/fs/cgroup/cpuset,cpu,cpuacct/cpu.cfs_quota_us
-1

这里值得注意的是cpu.cfs_quota_us为-1，这意味着我的pod没有设置cpu使用的上限。实际运行时可以突破上面yaml定义的4核的限制，这样的配置形式本质上是VPA的结果，VPA通过将CPU资源的分配模式从cpu.set切换到cpu.share，这样可以更大程度地榨取物理机的CPU的资源。

这样如果我当前pod的cpu使用率足够高，是完全可以影响同宿主机上的其他pod（也不是太容易，比较我的pod权重低），相当于当前物理机上的pod全部运行在一个大池子中，所有的容器都是依靠cpu.shares来进行资源抢占，以达到CPU利用率最大化的目的。这也就是为什么经常看到我们的pod的cpu使用率会被宿主机上其他pod拉起来，这种现象也就是我们经常说的 **“超卖”** 。

当然如果你的业务是核心业务，对稳定性要求很高的情况下，那么通常都是设置资源使用上限，以防止资源被超卖带来的稳定性问题。

## Kubernetes(K8S)

随着Docker的不断发展，各家厂商和公司开始拥抱Docker，Docker集群的规模也越来越大，容器越来越多。这样带来了大规模容器管理的难题，比如如何进行集群发布回滚、运维监控等问题。当然这也是Docker面临的问题，Docker虽好但是用户最终的目标还是要部署他们的应用、网站。所以Docker随后推出了Swarm来解决容器管理的问题，随后推出Compose来解决容器编排部署问题，这也将Docker的繁荣推到了最高潮。与此同时其他的厂商也没有闲着，比如，2014年Google率先开源了Kubernetes，作为容器的管理和编排的组件。

Docker的日益强大，随之而来的是社区对于Docker商业化的担忧。而且尤其是Docker公司在Docker项目的发展上的强硬态度，不断挑战着生态内的多家公司的权益。于是在2015年Google、Red Hat等公司联合成立了CNCF基金会，而CNCF摒弃了Docker Compose的方案，主要确立了以Kubernetes的容器编排和管理能力为核心的发展方向。因为Kubernetes本身是在Google内部发展多年产物，很多理念都很超前，这些耳目一新的理念推动了Kubernetes在社区的飞速发展。2016年Docker宣布将Swarm收回集成到Docker内部，使得Docker生态变得越发封闭。而反观Kubernetes则采取更为开放的插件化发展方向变得不断壮大，直到2018年Docker实际上已经在这场竞争中失败，竞争大幕缓缓落下。

对于Docker它核心要解决的是应用部署和资源隔离等问题。但是对于一个实际的生产环境，实际需要的是包括应用打包、部署、编排、容灾等等一系列的解决方案，也就是我们经常称为CI/CD的持续交付和持续集成的解决方案。

相比于Docker，K8S更聚焦在CI/CD的全流程解决方案上，更注重编排。虽然在漫长的竞争之中，Docker也做过容器编排，但是由于它对于开源社区的“傲慢”和一些其他的因素，最终还是没有竞争过Google + Redhat 领衔的K8S，K8S实际上已经成为了云原生的C位和实际标准，而Docker基本上沦为了容器运行时的一个”驱动“。

## K8S的基础架构

![](<../images/redirect_104.png>)

K8S架构还是比较清晰的，在宏观上的组成主要由Master和Node两种角色的节点组成：

1. **Master：** Kubernetes集群的控制平面，主要负责管理和调度集群状态。
2. **Node：** 是Kubernetes集群中的工作节点，负责实际承载和运行应用程序容器。

再细化一些，K8S的各个组成模块以及对应的功能如下：

1. **API Server:** 提供Kubernetes API的访问接口，是集群组件与Kubernetes交互的入口。
2. **Controller Manager:** 监控集群的状态并确保集群的当前状态与期望状态相符。它会处理Node、Pod、ReplicaSet等的创建、删除和更新等操作。
3. **Scheduler:** 根据资源需求和调度策略将新的Pod分配到合适的Node节点上。调度器会分析每个Node的资源使用情况、污点/容忍性等条件来做出最优的调度决策。
4. **etcd:** 存储集群的所有状态数据，包括所有的配置和对象的状态。etcd是一个高可用的键值存储数据库，确保数据的持久性和一致性。
5. **Container:** Node节点上运行具体的应用和服务。每个Node上通常运行多个Pod（多个容器的集合）。
6. **Kubelet:** 每个Node上运行一个Kubelet，它负责与Master节点进行通信，并根据Master节点的指示来创建、管理和监控Pod。
7. **NetWorking:** 负责网络代理和负载均衡，处理服务的请求，将请求转发到适当的Pod.

这些组件你看了之后可能有点不知所云的感觉，如果你很疑惑里面的一些内容，那么你可以深入学习一下K8S。不过你只需要明白K8S实际上是解决了应用集群的管理和部署问题，它的核心能力是通过容器镜像在整个集群的多个节点上部署我们的应用。只不过这些部署之后的容器实际是以POD形式而存在的，而不是我们通俗理解的容器。

### 如何理解POD

你可能会有疑问，POD具体指的是什么，我们实际使用的不应该是容器吗？为什么又出来一个POD。没错，看上去一个容器确实就能满足我们应用程序的部署问题，那为什么要使用POD来描述一个应用部署的"实例"呢，POD又是什么呢？

![](<../images/redirect_105.png>)

POD你可以理解为共享了某些资源的一组容器的集合，K8S在部署的时候会把多个容器进行打包到一起部署，打成的这个包就称为POD，通常在一个POD中的容器共享PID nameSpace、Mount nameSpace和Network nameSpace。

之所以要使用POD而不是直接使用Container来部署，主要有以下几点考量:

1. 对比传统的操作系统内部署的应用程序，它主要反映的是一个进程。那么在云计算环境下，一个容器就是一个进程，而往往实现一个应用程序不单单只是靠一个容器来实现，它还需要额外的配套环境，比如日志收集、监控探针和sidecar的service mash组件等等，所以 **POD则被抽象成"虚拟机"的概念、而容器则是一个一个进程** 。
2. K8S脱胎于Google，在Google内部打磨了很多年，最终开源，这里面沉淀了很多Google面临的业务场景沉淀下来的经验，就是一个应用部署往往需要多个组件相互协作。它们需要共享相同的 namespace，而这又会带来哪个容器来定义这一组共享资源的问题，所以索性使用POD来做资源的统一定义，来避免这种容器构建顺序依赖的问题。
3. 使用POD可以集中式管理所有容器的生命周期，如果Pod需要重启，所有的容器也会随之重启，这种设计简化了容器之间的依赖关系管理和资源回收。

**记住一点：** POD是K8S体系内的一等公民，所有的调度和分配都是围绕POD展开的，而POD的本质也是一个容器，这个容器和其他业务容器共享相同的PID namespace、Mount namespace和Network namespace。

我们目前使用的持续集成平台底层基础设施也都是基于K8S的，可以看一下我们自己机器的pod都是由哪些容器组成的。这一个过程可以在机器（诺曼底上可以看到）的YAML文件中进行查看，你可以通过搜寻containes标签得到这些POD中的容器，常见的主要有staragent、logtail等等，具体可以参考自己的应用：

## 以开源的CI/CD流程为例来说明一下K8S如何被使用

为了加深你对部署这一个过程的体感，我们以一个开源的CICD的集成流程来看一下对于容器镜像的部署过程是怎样的：

![](<../images/redirect_106.png>)

1. 应用开发者将代码push到gitlab。
2. jenkins等开源部署集成平台从gitlab拉取指定的分支代码。
3. jenkins通过使用本地的编译环境通过各种制品仓库的api拉取对应依赖包并使用编译（maven、gradle）工具进行代码编译打包。
4. 基于编译好的应用程序包，使用预先定义好的Dockerfile模板构建容器镜像。
5. 通过私有的Docker仓库的API，将Docker镜像push到仓库中。
6. 使用预定义好的部署脚本生成deployment配置yaml脚本。
7. 使用K8S的API提交deployment部署脚本。
8. K8S基于deployment部署脚本开始在不同的worker节点上拉取镜像、启动pod。

如上述流程所述一个部署流程就完成了，当然实际上Aone的实现应该会比这种复杂的多，因为不是很清楚Aone的具体集成部署流程（没找到资料），所以只能使用开源方案进行简单的交代，整体流程上应该大同小异。

```java
        try {
            // 创建 redis 连接
            jedis = new Jedis("service-redis.redis-default.svc.cluster.local", 6379);
            jedis.auth("test");
            // 验证连接
            System.out.println("Connection to server successfully " + "service-redis.redis-default.svc.cluster.local");
            // 设置一个 key
            jedis.set(key, value);
            // 获取并打印该 key 的值
            value = jedis.get(key);
            System.out.println("Stored string in redis: " + value);
        }catch (Exception e){
            System.out.println("Connection to server error " + e.getMessage());
            e.printStackTrace();
            value = "get key error....";
        }finally {
            if (jedis != null) {
                jedis.close();
            }
        }
        return value;
    }
}
```
